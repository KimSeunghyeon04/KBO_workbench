## 공통 로직 개선

### 1. 교체 선수의 새 역할을 기준으로 판단해야 한다 — 우선

수비위치 변경이면 항상 `fielder`로 반환하고, 일반 교체에서는 문장 전체에 `투수`가 있는지
검사한다. 그 결과 야수가 투수가 되는 경우와 투수가 야수가 되는 경우 모두 잘못 분류된다.
4경기에서 한 행씩 고쳐 89개의 후속 차단을 없앴다.

- 소유 모듈: `packages/collection/src/naver/lexicon.ts`의 `substitutionRole`,
  `event-emitter.ts`의 교체 이벤트 생성.
- 개선: 명시된 incoming position을 우선하고, 문장에서도 들어오는 쪽과 나가는 쪽을 분리한다.
  새 수비위치·타순·선수 identity를 함께 보존한다. 대타의 재교체도 현재 타석 문맥과 대조한다.
- 회귀 기준: 야수의 투수 등판, 투수의 야수 전환, 더블 스위치, 대타의 재교체를 비식별 fixture로 검증한다.

### 2. 주자 이름과 플레이 전체 관찰 상태의 충돌을 구분해야 한다 — 우선

07-09와 03-11 키움 경기에서 원문은 타자가 1루에서 2루로 더 진루했다고 명시하지만,
정규화된 행은 다른 주자 ID를 가리켰다. `resolveRunner`는 목적지 관찰값에 650,
유일한 이름 후보에 600의 강도를 주므로 플레이 전체 스냅샷이 행의 명시적 이름을 이긴다.
그 뒤 이동 중복, 타석 중첩, 다른 선수의 투구라는 연쇄 오류가 발생한다.

- 소유 모듈: `packages/collection/src/naver/player-resolver.ts`의 `resolveRunner`.
- 개선: 행의 명시적 선수와 플레이 전체 관찰의 용도를 분리하고, 같은 플레이 안에서 타자가
  주자가 된 이후의 추가 진루를 인식한다. 충돌을 단순히 한쪽 후보 강도를 올려 덮지 않는다.
- 회귀 기준: 기존 주자와 타자 주자가 같은 베이스를 차례로 사용하고, 이후 득점까지 이어지는
  연속 행을 검증한다. 이번 사례는 ID와 두 미해결 행을 바로잡자 기존 compiler가 정상 계산했다.

### 3. 피치클락 포수 위반 자동 볼을 인식해야 한다 — 우선

종류 판정의 정규식이 `투수|타자`만 포함한다. 05-22 한화–NC의 포수 위반은 안내문으로 남아
볼 하나가 누락되었고, 이후 볼넷과 타석이 연쇄적으로 어긋났다.

- 소유 모듈: `packages/collection/src/naver/lexicon.ts`의 종류·투구 판정.
- 개선: 포수 위반을 포함한 명시적 자동 볼/스트라이크와 단순 경고를 구분한다.
- 회귀 기준: 자동 볼은 카운트에만 반영하고 실제 투구 수에 포함하지 않는다. 경고만 있는 행은
  카운트를 바꾸지 않는다. 이번 한 행 정정으로 17개 차단이 해소되었다.

### 4. 종료 뒤 반복 중계와 다음 타자 표시를 별도로 처리해야 한다

5경기에서 종료 구간의 연속 행이 동일하게 재등장했다. 별도 2경기에는 경기 종료 뒤 실제
투구·타석 결과·새 반이닝 시작이 없는 다음 타자 표시만 있었다.

- 개선: block revision과 반복 구간의 이벤트 내용·순서·선수·투구 관찰을 함께 확인한다.
  `sourcePitchId` 하나를 일반 중복 제거 키로 쓰지 않는다.
- 원본 증거는 남기고 중복 관찰임을 표시한다. 실제 연장전 행이나 수정된 중계까지 제거하지 않는다.
- UI에는 중복 후보 구간을 나란히 비교하고 원자적으로 적용하는 보조 기능이 유용하다.
  이번에는 59행을 API atomic batch로 처리했으므로, 화면만으로 같은 작업을 반복하는 비용이 크다.

### 5. 야수선택의 책임투수 계산에서 주자의 마지막 이동만 사용해야 한다 — 우선

05-18 삼성–롯데 5회말에는 기존 투수의 주자가 아웃되고, 같은 플레이에서 다른 주자가
1루 → 2루 → 3루로 이동한다. `inheritFielderChoiceResponsibilities`가 중간 이동을 모두
최종 베이스 배열에 배치해 동일 주자를 두 베이스에 포함시킨다. 책임 slot을 배정한 뒤
runner ID로 Map을 만들 때 앞의 배정이 뒤에서 덮여 기존 투수의 책임이 사라진다.

- 소유 모듈: `packages/game-core/src/compiler/plate-play.ts`의
  `inheritFielderChoiceResponsibilities`.
- 확인된 결과: 공식 투수 실점 3/2를 2/3으로 계산한다. 총점은 같아도 투수별 귀속이 틀린다.
- 개선: 주자별 마지막 이동으로 최종 점유를 만들고 최종 주자 유일성을 검증한다.
  같은 runner의 여러 이동, 대주자, 다수 승계주자, force/tag out을 함께 회귀 검증한다.
- 이 경기는 책임투수를 수동 지정해 통과시키지 않고 검토 상태로 유지했다.

  필요하다. 예정 이닝을 임의로 늘리거나 가상의 아웃을 추가해서 해결하면 안 된다.

## 추가 분석: 공통 원인과 영향 범위

이 절은 위 실사용 결과와 추가 읽기 전용 조회를 분석한 내용이다. 추가 데이터 보정이나
DB revision 생성은 하지 않았다.

### 수치의 의미

- 최초 적재 가능 비율은 758/779, 약 97.3%다. 보정 후 적재 비율은 약 99.2%다.
- 검토 대상 21경기 중 15경기, 약 71.4%를 기존 계약과 compiler 안에서 정정했다.
  이는 수집 해석 개선으로 수동 작업량을 줄일 여지가 크다는 근거다.
- 이 수치는 보유 자료의 처리율이다. 전체 시즌 수집 완전성이나 모든 통계의 정확도는 아니다.

| 보정 원인군                      | 경기 수 | 해소된 차단 수 |
| -------------------------------- | ------: | -------------: |
| 반복 종료 구간·종료 뒤 타자 표시 |       7 |             54 |
| 교체 역할·대타 재교체            |       5 |             97 |
| 주자 identity와 후속 이동 연결   |       2 |             75 |
| 포수 피치클락 자동 볼            |       1 |             17 |
| 합계                             |      15 |            243 |

차단 243개는 독립적인 오류 243개가 아니다. 같은 원인이 이후 상태와 집계에 전파된 결과가
크게 포함된다. 개선 성과는 차단 개수보다 수동 개입 경기 수, 경기당 보정 명령 수,
추가 원문 확인이 필요한 경기 수로 판단하는 편이 적절하다.

### 해석 단위가 다른 증거를 구분해야 한다

주자 문제는 행의 선수와 플레이 전체의 최종 관찰값을 혼용했고, 교체 문제는 나가는 역할과
들어오는 역할을 혼용했다. 책임투수 문제는 이동 경로의 중간 지점과 최종 점유를 혼용했다.
반복 종료 중계도 개별 행의 identity와 block의 반복·revision 의미를 함께 다뤄야 한다.

정규식이나 후보 점수만 바꾸기보다 각 증거가 어느 행·플레이·시점을 설명하는지 먼저
정의해야 한다. 이 역할은 collection과 단일 compiler에 두며 UI가 별도 야구 규칙을 계산하지 않는다.

### 이미 봉인된 경기의 책임투수 검증 후보

2025년 DB current의 typed fact를 읽기 전용으로 조회했다. 야수선택 2,277플레이가
720경기에 있었고, 동일 주자의 safe 이동이 여러 번 기록된 그룹은 159개였다.
그중 승계주자 아웃까지 동반하는 5플레이·5경기에서 현 책임투수 함수의 중간 최종 점유 배열에
같은 주자가 중복으로 들어가는 패턴을 확인했다.

| 경기 ID             | 구간  | 타석 결과 원장 sequence |
| ------------------- | ----- | ----------------------: |
| `20250415HHSK02025` | 7회초 |                     344 |
| `20250510NCOB02025` | 6회초 |                     314 |
| `20250601SSLG02025` | 7회말 |                     488 |
| `20250720NCHT02025` | 8회말 |                     470 |
| `20250824LGHT02025` | 7회초 |                     366 |

sequence는 0부터 센다. 위 5경기의 실제 실점 귀속 오류를 확정한 것은 아니다.
중간 중복이 최종 책임 배정이나 이후 득점에 영향을 주지 않는 경우도 구분해야 한다.
보류 중인 05-18 삼성–롯데와 함께 수정 전후 책임주자·투수별 실점·projection을 비교할
회귀 검증 대상으로 삼는다. 필요하면 새 correction revision으로 반영하고 기존 봉인 행은 유지한다.

공식 비교는 제공된 선택 필드만 검증하고, 재생 hash는 동일한 저장 결과인지 확인한다.
따라서 적재와 hash 검증 통과를 모든 야구 의미의 독립적 검증으로 해석해서는 안 된다.

### 작업 완료를 DB 저장과 구분해서 기록해야 한다

`ImportJobManager.run`은 DB import 완료 후 staging 정리를 수행하고, 그 다음 job을 성공으로
표시한다. 코드상 DB commit 이후 파일 정리가 실패하면 DB에는 revision이 있지만 job은
실패하고 revision 정보는 비어 있을 수 있다. 이번 운영에서는 발생하지 않았으며 장애 주입은 하지 않았다.

영속 이력 설계에는 DB 저장 여부와 후속 정리 상태가 필요하다. 복구 시 game ID·document hash·
DB revision을 대조해 이미 저장된 작업을 식별하고 필요한 정리를 마쳐야 한다.
기존 revision base 검사는 재시도 시 중복 적재를 막는 경계로 유지한다.

### UI는 탐색·선택·실행 상태를 분리해야 한다

- 탐색 상태는 기간·검색·필터·페이지다.
- 상세 선택은 현재 목록에 포함되는 경기여야 한다. 제외되면 닫는다.
- 실행 대상은 사용자가 확정한 범위와 경기 집합이다. 탐색 중 조용히 변하지 않으며 별도로 표시한다.
- 저장 상태, 검증 상태, 과거 작업 결과를 한 상태값으로 합치지 않는다.

보정 화면은 원인 후보와 원문 근거, 명령 적용 전후의 검증 변화를 이어서 보여주는 방향이 적절하다.
시간상 뒤에 나온 오류를 모두 종속 오류로 간주하지 않고, 같은 플레이와 실제 상태 의존성이
확인되는 범위에서 묶어야 한다. 원문 자체가 없는 경우에는 일반 편집보다 필요한 증거를 안내한다.

남은 6경기 중 코드·계약 검증을 먼저 진행할 대상은 책임투수, 연장 강우콜드, 쓰리번트 카운트
3경기다. 다른 3경기는 누락 행 또는 아웃 판정에 대한 추가 원천 증거 확인이 우선이다.
