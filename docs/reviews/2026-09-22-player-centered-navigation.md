# 선수 중심 분석 탐색

2026-09-22. 분석 기능을 먼저 고른 뒤 화면마다 선수를 다시 찾던 흐름을, 선수를 고르고 해당 선수의
분석 항목을 이동하는 흐름으로 바꿨다. API·계산·봉인된 데이터 계약은 유지한다.

## 화면 구조

분석 영역의 최초 진입 주소는 `/analysis/players`다. `/analysis`도 같은 목록을 표시한다. 작업 영역을
다시 열 때는 이전의 상세 주소와 검색 조건을 복원한다.

| 위치         | 제공 항목                                                                |
| ------------ | ------------------------------------------------------------------------ |
| 선수 분석    | 2020–2025 시즌, 투수/타자 유형, 이름·ID 검색으로 선수 선택               |
| 투수 선택 후 | 코스·결정구, 구질·움직임, 최근 변화, 배합·궤적, 등판·운용, 타자와 매치업 |
| 타자 선택 후 | 반응·성적, 선구안, 투수와 매치업                                         |
| 리그·경기    | 선수·팀 성적, 주루와 추가 진루, 구장 득점 환경, 경기 재생                |
| 분석 관리    | 분석 자료 품질, 분석 모델 관리                                           |

투수를 고르면 `/analysis/pitch-location`, 타자를 고르면 `/analysis/batter-profile`을 연다. 상세
상단에는 현재 선수와 조회 범위, 분석 항목, `선수 변경` 링크를 표시한다. 리그 순위표와 주루 집계는
개별 선수 지표로 바꾸지 않고 기존 집계 범위를 유지한다.

## URL과 기존 동작

- 선수별 이동에는 `pitcher` 또는 `batter` ID, `season`, `competition`, `dateFrom`/`dateTo`를
  전달한다. 표시 이름으로 다른 선수와 병합하거나 선수 identity를 새로 만들지 않는다.
- 탐색 목록은 `role=pitcher|batter`, 검색어 `q`, 1부터 시작하는 `page`를 사용한다. 검색어 입력은
  history를 replace한다. 유형·시즌·범위·검색이 바뀌면 페이지를 초기화하고, 시즌 변경은 이전
  시즌의 날짜 조건을 제거한다. `선수 변경`은 현재 유형·시즌·범위의 목록을 연다.
- 새 목록은 확인된 정규시즌 `regular`가 기본이다. 기존 구질·선구안 주소를 경기 종류 없이 직접
  열면 `all`, 다른 선수별 화면은 `regular`인 기존 기본값을 유지한다. 기능 이동 링크에는 실효
  경기 종류를 명시하므로 구질·선구안으로 이동하더라도 표본 범위가 바뀌지 않는다.
- 투수 변화의 기본 종료일은 기존과 같이 선택 시즌의 12월 31일이다. 다른 화면으로 이동할 때도
  현재 적용한 종료일을 전달한다. 기존 페이지의 시즌 보정과 잘못된 조건 처리도 유지한다.
- 매치업에 들어갈 때 `playerRole=pitcher|batter`를 함께 전달해 탐색 중인 주선수를 유지한다.
  상대 선수를 고르더라도 공통 분석 항목은 주선수의 유형을 따른다. `playerRole`이 없는 기존
  매치업 주소는 투수를 기준으로 탐색 항목을 표시한다.
- 다른 기능으로 이동할 때 군집·차트·카운트·구종 등 기능 고유 조건은 옮기지 않는다. 현재 항목을
  다시 눌러도 현재 query를 유지하고, 브라우저 뒤로 가기는 이전 화면의 조건을 복원한다.
- 사이드 메뉴와 별도로 유효한 상세 경로 목록을 유지한다. 데이터 관리/분석 전환에서 메뉴 밖의
  상세 주소와 query·hash를 복원하며 외부 주소나 알려지지 않은 경로는 복원하지 않는다.

## 목록의 데이터 범위와 비용

기존 `pitcherCatalogQueryOptions`/`batterCatalogQueryOptions`를 그대로 사용한다. 선택한 유형의
catalog만 조회하고 상세 분석은 선수 선택 뒤 해당 페이지가 요청한다. catalog는 선택한 경기 범위의
실제 투구 기록이 있는 선수만 반환한다. 투구 없이 대주자로만 출전한 선수 등을 포함하는 전체 등록
명단으로 해석하지 않는다. 이름·ID·실제 투구 수만 표시하며 팀이나 포지션을 추정해 채우지 않는다.

서버가 실제 투구 수 내림차순, ID 순으로 반환한 순서를 유지한다. 검색은 이름·ID의 NFC 정규화와
대소문자 정규화 뒤 수행하고, 받은 목록에서 최대 48명만 DOM에 표시한다. 검색과 페이지 이동을
이유로 목록을 다시 요청하지 않는다. 검색 결과가 없는 경우와 해당 범위에 기록된 선수가 없는
경우를 구별하며 후자는 같은 범위의 자료 품질로 연결한다. 조회 실패는 재시도 버튼을 제공한다.
카드 링크는 이름을 접근성 이름으로, 실제 ID를 `aria-describedby`로 연결해 동명이인을 구별한다.

## 모듈 경계와 공통 필터

`AnalysisPlayersPage`는 목록의 검색·페이지·선택을, `player-analysis-navigation`은 역할별 항목과
링크 생성을, `PlayerAnalysisFrame`은 현재 선수의 탐색 바를 담당한다. `AppShell`은 상위 메뉴와
작업 영역의 마지막 주소를 관리한다. 분석 결과나 선수 선택 상태를 별도 전역 저장소로 복제하지
않는다.

공통 frame의 catalog observer는 `enabled: false`다. 기존 페이지와 동일한 query key 및 strict
catalog 응답을 관찰하며 자체 fetch, 다른 분석의 선행 조회, 별도 polling을 만들지 않는다. 같은
시즌·유형·경기 종류·날짜의 목록 identity를 공유하고 implicit/explicit `all`을 같은 키로 취급한다.
query의 갱신 정책과 실제 요청은 기존 페이지가 소유한다. 기존 페이지의 선수 결정 규칙도 유지하며
구질 화면의 첫 선수 fallback을 탐색 표시에 동일하게 반영한다.

`playerNavigationScope`는 링크를 만들 때 기존 페이지의 기본값을 읽는 표현 모듈이다. 조회 검증을
대신하지 않는다. 향후 페이지 기본값을 변경할 때는 navigation의 범위 회귀도 함께 갱신해야 한다.

공통 `PitcherScopeFields`는 `AnalysisFilterBar`로 시즌·투수를 기본 조건에 표시하고 경기 종류·날짜와
배합 등의 추가 입력은 native details의 `세부 조건`으로 묶는다. 매치업의 타자 선택은 `primary`
슬롯으로 기본 조건에 남긴다. 조건 변경·URL·요청·계산은 기존 페이지에 두고 표시 배치만 공유한다.

## 검증

- 선수 탐색 8개 테스트 통과: 선택 유형의 목록만 조회, 범위 유지 링크, 48명 렌더 제한, 이름·ID
  검색, 검색 history replace, 동명이인 ID 설명, 빈 목록/오류 재시도, 잘못된 범위의 요청 중지와
  시즌 변경 시 날짜 초기화.
- 공통 catalog query 6개 테스트 통과: 같은 범위의 요청 공유, 유형·시즌·범위 분리, 취소 전달과
  strict 응답 검증. 새 목록 구현 뒤 웹 TypeScript·대상 ESLint·Prettier 검사 통과.
- 선수별 탐색 10개 테스트 통과: 선수·시즌·기간·경기 종류 유지, 활성 링크의 고유 조건 보존,
  뒤로 가기, 타자 기준 매치업, 기존 기본값과 구질의 선수 fallback, 탐색 바의 추가 요청 없음.
- 전체 단위 테스트 980개 통과, DB DSN이 필요한 75개 skip. lint, format:check, typecheck,
  schema:game:check, build와 diff 공백 검사 통과.
- 실제 브라우저에서 류현진의 코스→배합, 김도영의 반응→매치업을 열어 선수와 범위가 유지되는
  것을 확인했다. 390px 모바일 폭에서 선수 목록·공통 메뉴·매치업에 가로 넘침이 없었고, 키보드로
  선수 목록 복귀도 확인했다. 임시 viewport는 원래 크기로 복원했다.

- 격리 Compose E2E 통과: 기본 진입→선수 검색→투수 코스/구질→선수 변경→타자 반응/선구안,
  선수·시즌·경기 종류·기간 유지와 1280px/390px 배치를 검증했다. 기존 수집·보정·기록정정·DB·재생,
  차트·군집·키보드·백업/복원·6종 모델 작업도 통과했다. 테스트 프로젝트
  `kbo-stage6-38608-019b8715`의 임시 컨테이너·네트워크·볼륨 정리를 확인했다.

첫 E2E 실행에서는 검색 직후 URL을 동기적으로 검사하던 테스트의 타이밍 오류가 발견됐다.
예상 URL과 실제 필터 결과를 기다리도록 검증을 수정한 뒤 전체 흐름을 다시 실행해 통과했다.
검증 로그는 로컬의 `analysis/commit-preparation/20260922-player-navigation/`에 보관한다.
최종 E2E 로그는 `e2e-rerun.log`다. 운영 데이터와 API·계산 계약의 변경은 없다.
