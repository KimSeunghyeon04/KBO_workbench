# 분석 화면의 해석 용이성 점검

2026-09-24. 선수 탐색, 투수·타자 분석, 기본 기록, 주루와 모델 설명의 해석 용이성을 점검했다.
검토 기준 소스는 `4b81ee3b9baa9385e987e9efecc766863d577bde`다.

이 문서는 수정 전 점검 기록이다. 이후의 반영 내용과 검증은
[개선 결과](2026-09-24-analysis-comprehension-improvements.md)에 정리했다.

## 판단

선수 중심 이동과 일부 지표의 분모 설명은 잘 되어 있다. 그러나 현재 화면만으로 분석 결과를
일관되게 해석하기에는 보완이 필요하다. 가장 먼저 고칠 것은 비교 중 선수·조건이 바뀌는 동작과
지표 정의·단위의 모호함이다. 그 다음으로 핵심 결과와 비교 기준을 상세 표보다 먼저 제시해야 한다.

브라우저에서 코스·결정구는 19.9% Whiff와 1,162스윙 중 231헛스윙을 함께 보여 주었다.
계산은 이해할 수 있지만 해당 값이 어떤 비교 집단보다 높은지까지는 알 수 없다. 최근 변화는
비교 기간·방법 설명과 긴 표를 제공하지만 변화의 방향·크기·불확실성을 한 번에 읽을 요약이 없다.
이는 계산 결함과 구분되는 정보 구성상의 판단이며 사용자 테스트 결과는 아니다.

## 증거 수준

Graft로 호출 경로를 확인한 뒤 화면 문구, 필터 전달, 집계 구현과 기존 테스트·정책 문서를 대조했다.
최신 프론트엔드를 로컬 전용 Vite(5173)로 실행하고 운영 API(8080)의 실제 수집 데이터를 읽었다.
선수 목록, 손주영의 코스·구질·최근 변화·기본 기록, 김도영의 반응→선구안 이동 및 시즌 변경,
주루 화면을 브라우저로 확인했다. 기본 기록의 정상 표시는 기존 통계 미리보기 API(5184)로
해당 경로만 연결하여 확인했다. 각 개선 항목에서 브라우저 재현과 코드 검토를 구분한다.
모든 선수·시즌 조합, 모바일 반응형, 보조기술 전체 사용성을 검증한 것은 아니다.
앱 코드·분석 정의·운영 데이터는 변경하지 않았다. 소스 링크의 줄 번호는 검토 시점 기준이다.

## 배포 상태와 검토 범위의 제한

- 운영 프론트엔드(8080)는 이전 메뉴 구조다. 실제 상단 `분석` 링크는 `/analysis/pitch-shape`로
  이동하며, 최신 `/analysis/players` 주소를 직접 열면 본문이 비고 `No routes matched`가 기록된다.
  운영의 모든 분석이 열리지 않는다는 뜻은 아니다. 선수 중심 UX 평가는 최신 코드 미리보기 기준이다.
- 최신 UI를 운영 API에 연결하면 선수별 기본 기록이 `성적 조회 범위가 요청과 다릅니다`로 실패했다.
  이 상태를 기본 기록 표 자체의 설계 결함으로 분류하지 않는다. 프론트엔드와 API를 같은 계약으로
  배포하는 확인이 필요하다. 클라이언트 검증을 완화하는 해결은 적절하지 않다.
  같은 GET 요청의 `playerId=67143`를 8080은 응답 query에서 빼고 리그 전체를 반환했으며,
  5184는 해당 선수 한 행을 반환했다. 기본 기록 경로만 5184로 연결한 뒤 손주영 30경기·153이닝·
  ERA 3.41·ER 확인 30/30 표시를 확인했다. 운영 프록시나 컨테이너는 변경하지 않았다.
- 구종 기대 효과에서는 `현재 원천에 맞는 학습 모델이 없습니다`가 표시됐다. 기대값이 준비된
  모델의 전체 시각화는 이번 브라우저 점검 범위 밖이다. 검증 연도 문구는 코드로 대조했다.

## 개선 사항

### 1. 구질 화면의 구종 필터 적용 영역을 표시해야 한다

**재현 조건:**
`/analysis/pitch-shape?season=2025&competition=regular&dateTo=2025-12-31&pitcher=67143&type=슬라이더`를
열고, 산점도 아래의 `구종 구성과 월별 변화`, `진입각 VAA/HAA`, `구종 기대 효과`를 확인한다.

**브라우저 증거:** 최신 UI와 8080 운영 API에서 2025년 손주영(ID 67143), 정규시즌,
종료일 2025-12-31 조건으로 재현했다. 슬라이더 선택 후 산점도는 306구만 표시하지만 구종
프로필에는 직구 1,309구·커브 570구 등 전체 구종이 그대로 남았다. 진입각·기대 효과 패널의
필터 범위는 아래 코드 경로로 확인했으며, 이 브라우저 재현 수치에 포함하지 않는다.

**코드에서 확인한 동작:** 구종 선택은 산점도의 투구와 기대 차이 표에 적용된다. 하단 구종
프로필에는 전체 `data.profile`이 전달되고, 진입각·기대 효과의 조회에는 시즌·경기 종류·기간만
전달된다. 따라서 이 세 패널은 상단 구종 선택과 별개로 전체 구종을 표시한다.

**예상되는 오해:** 상단의 `구종`을 페이지 전체 조회 조건으로 읽으면 아래 표의 표본·평균도
선택 구종에 한정된 값이라고 생각할 수 있다. 분포 구간 비교에는 필터 미적용 설명이 이미 있지만,
이 세 패널에는 같은 범위 안내가 없다.

**권장 개선:** 현재 계산 범위를 유지하면서 패널 제목 옆에 `전체 구종 · 상단 구종 필터 미적용`을
표시한다. 또는 필터를 `산점도·기대 차이 표 표시 조건`으로 명명해 적용 영역을 분명히 한다.
클러스터 필터도 같은 원칙으로 설명하며, 모든 패널에 같은 필터를 적용하는 것으로 임의 변경하지
않는다.

### 2. 배합의 활성 상황 조건을 접힌 상태에서도 보여 주어야 한다

**재현 조건:** `/analysis/pitch-sequences?season=2025&strikes=2&previousType=직구`를 연다.
또는 `세부 조건`에서 첫 구종과 두 번째 스트라이크를 지정한 뒤 조건을 접는다.

**코드에서 확인한 동작:** 첫 구종·다음 구종·카운트는 실제 조회에 적용된다. 이 입력들은 모두
공통 필터의 세부 조건 안에 있으며, 접힌 요약에는 경기 종류와 기간만 표시된다. 해당 값이
URL에 남아도 요약만으로는 활성 조건을 알 수 없다.

**예상되는 오해:** 첫 공이 직구이고 두 번째 공이 2스트라이크인 경우만 남은 배합 결과를 선수의
전체 배합 결과로 읽을 수 있다. 주소로 다시 방문하면 세부 조건은 기본적으로 닫혀 있다.

**권장 개선:** `직전 직구 · 두 번째 2스트라이크`처럼 설정된 상황 조건을 요약이나 조건 칩에
표시하고 각각 지울 수 있게 한다. 시즌·선수·경기 종류·기간은 상황 조건 초기화와 분리한다.
URL에서 지원하는 타석 좌우·표본 조건도 같은 방식으로 표시해야 한다.

### 3. 배합 표의 비율별 분모와 평균별 유효 표본을 구분해야 한다

**재현 조건:** `/analysis/pitch-sequences?season=2025`에서 `두 구종 조합` 표의 설명과
Whiff%, 기하 쌍, 구속 차, 도착 코스 차를 함께 읽는다.

**코드에서 확인한 동작:** 표 위에는 `성과의 분모는 두 번째 공입니다`라고 적혀 있다. 실제
Swing%·루킹%의 분모는 조건을 충족하는 두 번째 실제 투구 수이며, Whiff%의 분모는 그중 스윙
수다. `기하 쌍`은 공통 비교면에서 위치를 계산할 수 있는 쌍 수다. 각 거리·시간·구속 평균은
해당 값이 null이 아닌 쌍만 별도로 사용하므로, 모든 평균이 동일한 기하 쌍 수를 분모로 삼는 것은
아니다.

**예상되는 오해:** 모든 비율을 실제 투구 수로 나눈 값으로 읽거나, 나란히 있는 평균의 표본 수가
같다고 생각할 수 있다. 구속 차와 시간차가 어느 방향의 차이인지도 집계 표의 열 이름만으로는
알기 어렵다. 현재 두 번째−첫 번째 시간이라는 설명은 아래 개별 투구 비교에 있다.

**권장 개선:** `성과는 두 번째 공의 결과를 집계합니다`로 대상과 분모를 구분하고, 표 가까이에
`Swing%=스윙/쌍`, `Whiff%=헛스윙/스윙`, `루킹%=루킹/쌍`을 명시한다. 각 평균의 유효 표본 수를
함께 보여 주고, 시간차·구속차는 `두 번째−첫 번째`라는 부호 기준을 표시한다. `기하 쌍`에는
`y=23.8ft 공통 면 위치를 계산할 수 있는 쌍`이라는 정의를 붙인다.

### 4. 과거 시즌의 지도에 분석용 존 규칙을 명시해야 한다

**재현 조건:** `/analysis/pitch-location?season=2020&competition=regular`에서 코스 지도와
Zone%·Chase%의 설명을 확인한다.

**코드에서 확인한 동작:** 지도에는 `원천 도착면, 신장 기준 존`이라고 표시된다. 존 계산은
2024년까지의 시즌에 2024 신장 규칙을 적용하고, 2025·2026년에는 2025 규칙을 사용한다.
문서에서도 과거 시즌에 2024 규칙을 적용하는 것은 사용자가 정한 분석 기준이며, 당시 심판 존의
재현이 아니라고 명시한다.

**예상되는 오해:** 2020년의 지도와 존 안팎 지표를 당시 심판이 적용한 판정 존의 재현으로 읽을
수 있다. 시즌을 바꾸어 비교할 때 2024년과 2025년 사이의 존 정의 변화도 화면에서 드러나지
않는다.

**권장 개선:** 지도와 존 지표 안내에 `분석용 신장 기준 존 · 2024 규칙 적용 · 당시 심판 판정
존 아님`처럼 현재 시즌에 적용한 규칙을 표시한다. 2025년 이후에는 해당 규칙명을 바꾸고,
시즌 간 존 비율 비교 시 정의 변화가 포함된다는 점을 설명한다. 기존 존 계산 정책은 유지한다.

### 5. 조건 일치 선구안 비교에서 상황 조건을 보존해야 한다

**브라우저 재현:** 김도영(ID 52605)의 2025 정규시즌 반응·성적에서 `2스트라이크`를 선택했다.
화면에 활성 조건 칩과 `strikes=2`가 표시된 상태에서 `조건 일치 선구안 비교` 링크는
`/analysis/batter-discipline?season=2025&competition=regular&dateTo=2025-12-31&batter=52605`였다.
클릭 후 스트라이크 조건이 사라졌다. 코드상 구종·타석 좌우도 전달하지 않는다.

**영향과 개선:** 동일한 상황의 두 분석을 비교하는 것으로 읽지만 실제 분모는 달라진다.
대상 화면이 지원하는 상황 조건을 전달하고, 선구안 자체의 제외 규칙 때문에 달라지는 표본은
별도로 안내해야 한다. `조건 일치`를 단순 시즌·선수 일치의 뜻으로 사용하지 않는다.
[비교 링크 구성](../../apps/web/src/pages/pitch-outcomes-page.tsx#L276).

### 6. 시즌 변경 시 선택한 선수를 유지해야 한다

**브라우저 재현:** 김도영의 선구안에서 시즌만 2025→2024로 바꾸자 선수 리포트가
로하스(ID 67025)로 바뀌었다. URL에서도 `batter`가 사라졌다.

**영향과 개선:** 같은 선수의 연도별 비교를 시도하다 다른 선수의 결과를 읽게 된다.
선수 ID를 유지하고 해당 시즌 자료가 없으면 그 선수의 빈 상태를 보여 주어야 한다.

### 7. 최근 변화의 사용률을 %와 %p로 표시해야 한다

**브라우저 재현:** 손주영 2025 정규시즌 최근 3등판/이전 5등판에서 슬라이더 사용률이
최근 `0.17`, 이전 `0.12`, 차이 `0.05`로 표시됐다. 직구 사용률 차이의 95% 구간도
`-0.13 ~ 0.02`처럼 표시된다.

**영향과 개선:** 다른 화면의 사용률은 %인데 여기서는 0~1 비율이어서 읽는 규칙이 다르다.
비율은 원시 값에 100을 곱해 `%`, 비율 차이와 구간은 `%p`로 표기해야 한다.
표시된 두 비율을 반올림한 뒤 빼지 않고 원래 계산된 차이를 사용한다.
[공통 숫자 표시](../../apps/web/src/pages/pitcher-changes-page.tsx#L11),
[비율 계산](../../packages/game-core/src/pitcher-changes.ts#L151).

### 11. 기본 기록의 경기 수와 OPS 산출 원칙을 설명해야 한다

**브라우저 및 코드 대조:** 기본 기록의 `G` 열에는 별도의 집계 대상 설명이 없었다.
코드상 `G/경기`는 통계 fact가 있는 경기 수다. 무타석·무득점 출전 등을 포함하는
공식 출전 경기 수와 동일한 계약이 아니다. OPS는 반올림 전 OBP+SLG를 합한 뒤 표시한다.
따라서 표시된 OBP와 SLG를 더한 값과 OPS가 소수 셋째 자리에서 다를 수 있다.

**영향과 개선:** 계산 범위의 차이가 수집 누락 또는 산술 오류로 읽힌다. `G: 수집 원장에서
기록이 생성된 경기 수`와 `OPS: 반올림 전 OBP+SLG`를 표 근처 지표 안내에 명시한다.
공식 출전 경기 수를 제공하려면 설명만 고칠 일이 아니라 참여 사실의 별도 계약 점검이 필요하다.
[G 표시](../../apps/web/src/analysis/player-statistics-tables.tsx#L27),
[경기 집계](../../packages/persistence/src/player-statistics-repository.ts#L40),
[OPS 계산](../../packages/game-core/src/player-statistics.ts#L19).

### 12. 주루 표의 득점과 추가 베이스를 일반 기록과 구분해야 한다

**브라우저 및 코드 대조:** `선수별 주루`에는 `진루`, `추가 베이스`, `득점`이 표시되고
근처 설명은 SB/(SB+CS)·견제사·경기 수에 한정된다. 실제 집계는 기존 주자의 이동 행에 기반하므로
타자 자신의 홈런 득점은 포함하지 않는다. 추가 베이스는 이동마다 한 베이스를 초과한 거리다.

**영향과 개선:** 기본 기록의 총득점 또는 장타의 루타 수와 혼동할 수 있다.
`기존 주자 진루 횟수`, `초과 이동 베이스`, `기존 주자 득점`처럼 범위를 밝히고,
아래의 단타 추가 진루 성공률과도 정의를 구분해야 한다.
[표 표시](../../apps/web/src/pages/baserunning-page.tsx#L84),
[집계 입력 생성](../../packages/game-core/src/compiler/derived-facts.ts#L96).

## 권장 개선 순서

1. **비교의 연속성:** 5·6번의 필터/선수 유지부터 수정한다. 1·2번의 활성 조건과 적용 영역도
   항상 보이게 한다. 표시 조건과 실제 쿼리가 일치하는지 이동 회귀 테스트로 고정한다.
2. **숫자의 의미:** 3·7·8·11·12번의 분모·단위·집계 대상을 공통 지표 정의로 정리한다.
   4·9·10번의 분석 기준과 모델 상태도 값 가까이에 명시한다.
3. **결과 읽는 순서:** 선수·시즌·조건 → 핵심 변화 2~3개 → 비교 기준과 유효 표본 →
   그래프 → 상세 근거 표 순으로 배치한다. 월별·등판별 원자료 표는 필요할 때 펼치게 한다.
   예를 들어 최근 변화는 `직구 구속 +0.57km/h, 95% 구간 -0.02~+1.10`을 먼저 보여 주고
   방향이 확실하지 않음을 함께 읽을 수 있게 한다. 유의한 차이를 자동으로 실력 향상이라 부르지 않는다.
4. **비교 집단 명시:** 리그 기준을 제공할 때 시즌·구종·투타 좌우·상황과 유효 표본을 밝힌다.
   단순 전체 리그 평균을 능력 등급으로 전환하거나 표본이 부족한 구종을 순위화하지 않는다.
   비교 기준이 없는 수치에는 우열 색상을 임의로 부여하지 않는다.
5. **배포 일치 확인:** 운영 전환은 최신 UI와 호환 API를 한 묶음으로 검증한다. 이 점검에서는
   배포하지 않았다. 선수 목록 → 기본 기록 → 반응 → 조건 비교 → 시즌 변경을 실제 데이터로 확인한다.

공통화 대상은 지표 정의(단위·분모·방향), 적용 중인 조건, 관측/비교/제외 표본 표시다.
모든 분석 화면을 하나의 범용 테이블 컴포넌트에 맞추는 것은 권하지 않는다. 존 지도, 궤적,
등판 변화는 각각 읽는 목적이 다르므로 해당 모듈이 표현을 소유해야 한다.

## 검증 기록

- 브라우저의 실제 DOM·스크린샷과 코드 경로를 대조했다. 표본 값은 점검 시점의 수집 자료 기준이다.
- 이 문서만 추가했고 앱 코드·계산 규칙·운영 데이터는 바꾸지 않았다.
- 문서 포맷, 소스 링크 대상과 줄 범위, 최종 Git diff를 확인했다.
- 코드 변경이 없어 전체 단위·통합·E2E 테스트를 다시 실행하지 않았다. 위 브라우저 점검은
  정식 사용자 조사나 모든 분석 기능에 대한 회귀 테스트를 대신하지 않는다.
