# 분석 기능 성능 검증

2026-09-20, Windows/Node 24.19.0, Ryzen 5 9600X. DB/E2E는 격리 Linux 컨테이너의 PostgreSQL 16,
Node 24.18.0이다. 먼저 고정 fixture의 구현 검증을 기록하고, 마지막에 실제 6개 시즌 snapshot의
측정을 구분한다. 운영 DB에는 새 migration을 적용하지 않았다. repository/worker 측정은
HTTP·브라우저 렌더링을 포함한 API 지연 상한을 뜻하지 않는다.

## 계산과 직렬화

`pnpm performance:analytics`는 첫 실행과 이후 29회, 총 30회를 분리 기록한다. 첫 실행도
새 OS 프로세스/DB 캐시를 강제로 비운 cold start는 아니다. 학습은 합성 6시즌 자료이며
worker 전달·DB·파일 I/O는 제외한다. RSS는 각 반복 직후의 최대 관측값이며 연속 peak가 아니다.

| 작업                     |             입력 | 첫 계산 | warm 평균 | warm p95 | 직렬화 p95 |
| ------------------------ | ---------------: | ------: | --------: | -------: | ---------: |
| A10 후보 비교·최종 적합  |          7,200구 |   439ms |     515ms |    539ms |     0.40ms |
| A10 고정 모델 선수 요약  |          5,000구 |  9.26ms |    8.83ms |  10.68ms |     0.06ms |
| A14 Poisson/NB 비교·적합 | 2,880 팀·경기 행 |   242ms |     205ms |    218ms |     0.06ms |

최대 관측 RSS는 약 385MiB, 선수 요약 응답은 약 6.5KB다. A10의 전체 원시 자료와 설계 행렬은
학습 작업의 메모리를 사용한다. 처리량을 전체 시즌에 단순 비례 외삽해 시간/메모리를 보장하지 않는다.
실제 학습 CLI는 전체 시간을 출력하며 실패·취소·30분 제한에서는 모델 포인터를 공개하지 않는다.

## DB 조회와 실행계획

`pnpm test:e2e`의 `measure-analytics-queries.mjs`는 테스트용 `analysis-2024` 경기들을 확인한 뒤
같은 repository를 30회 읽는다. snapshot·SQL 왕복·hydration, 나머지 계산, 응답 직렬화를 나눠
측정하고 실제 실행한 7종 SELECT/WITH의 `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)`을 기록한다.
모든 쿼리는 읽기 전용이며 측정용 작은 fixture의 계획이다. 전체 시즌에서 인덱스 선택이 같다고
보장하지 않으며 준비된 모델의 6시즌 manifest 검증 비용은 이 모델 없는 조회 측정에 포함하지 않는다.

| 조회           | 첫 전체 시간 | warm p95 | DB 부분 p95 | 나머지 처리 p95 | SQL 수 |
| -------------- | -----------: | -------: | ----------: | --------------: | -----: |
| 타격 집계      |       7.16ms |   4.12ms |      3.64ms |          0.62ms |      6 |
| 투구 집계      |       3.69ms |   3.65ms |      3.34ms |          0.48ms |      6 |
| 구종 모형 입력 |      10.03ms |   8.44ms |      8.18ms |          0.27ms |      6 |
| 구장 환경      |       3.28ms |   3.21ms |      2.99ms |          0.24ms |      6 |
| 연속 투구      |       8.06ms |   7.53ms |      7.12ms |          0.71ms |      6 |

SQL 수에는 BEGIN/SET/COMMIT도 포함한다. 각 부분의 p95는 서로 다른 반복에서 나올 수 있어
합산하지 않는다. 쿼리 측정 프로세스의 최대 관측 RSS는 약 88.6MiB다. 실행계획과 원 수치는
`analysis/analytics-query-performance.json`, 계산 측정은 `analysis/analytics-performance.json`에 남긴다.

## 기존 경로 회귀

`pnpm performance`에서 558이벤트 컴파일 200회는 평균 4.60ms / p95 7.29ms,
재생 구성 500회는 평균 0.96ms / p95 1.42ms였다. 평균 10ms / p95 25ms 기준을 통과했다.

운영 배포 뒤에는 HTTP·브라우저를 포함한 최초 조회·재조회·동시 요청을 추가 측정한다.
초기 목표는 선수 p95 1초/시즌 집계 p95 2초이며 fixture 수치만으로 달성을 선언하지 않는다.

## 실제 수집 자료의 학습

운영 DB의 읽기 전용 snapshot 4,693경기에서 정규시즌 4,316경기를 확인했다. `analysis:validate`가
고유 검증 DB와 별도 workspace에서 실행했고 운영 서비스에는 공개하지 않았다. 실행 절차는
[실데이터 검증](real-data-validation.md)에 있다. Windows Node 24.19.0과 격리 PostgreSQL 16을
사용했다. 학습 중 일부 구현 테스트가 병행되었으며 아래 시간은 해당 실행의 관측값이다.

| 학습           | 조회 초 | 계산 초 | 저장 초 | 최대 관측 RSS MiB |
| -------------- | ------: | ------: | ------: | ----------------: |
| RE24           |   89.15 |    1.40 |    0.19 |               844 |
| 카운트 RE      |   95.06 |    3.76 |    0.13 |             1,832 |
| 승리확률       |   54.51 |   10.80 |    0.18 |               912 |
| 구장 효과      |   15.57 |    1.41 |    0.12 |               408 |
| 구종 기대 효과 |   35.32 |  176.28 |    0.43 |             5,142 |

구종 입력은 1,318,591구다. 전체 후보 학습은 maintenance 작업이며 화면 조회 때 실행하지 않는다.
메모리는 process와 worker 전체 RSS를 100ms 간격으로 관측한 값이다. 낮은 메모리 환경에서 같은
시간을 보장하지 않는다. 검증 도구는 모델을 하나씩 실행해 학습 간 메모리가 겹치지 않게 한다.

실데이터에서 발견한 병목은 다음처럼 수정했다.

- A10 월별 쿼리는 시즌 전체 투구/신장을 반복 결합하면서 30초 제한에 걸렸다. 선택 경기를
  materialize하고 경기별로 view를 확장해 조회 범위를 먼저 제한했다.
- 준비된 모델의 원천 검증은 6개 시즌 신장 조회를 반복해 선수 입력 읽기 한 번에 19.54초가
  걸렸다. 같은 snapshot의 유효 신장을 한 번 읽고 시즌별로 나눠 hash를 계산해 사전 측정에서
  1.05–1.10초로 줄었다. 원천 해시 및 변경 감지는 유지한다.
- 구장 집계는 전체 play를 두 번 정렬하지 않고 적용된 play의 첫·마지막 순번을 한 번 집계해
  원래 상태를 PK로 읽는다. 6시즌 입력 읽기가 34.91초에서 15.57초로 줄었다.
  이후 실행계획에서 이닝 요약이 팀·경기 행마다 1,440번 반복되는 것을 확인해 한 번 계산한
  결과를 재사용하도록 고정했다. 2025 조회 사전 비교는 2.68초에서 0.55초로 줄었으며
  응답 전체의 canonical hash가 동일했다. 위 학습 시간은 이 마지막 개선 전의 기록이다.
- A06 배합 조회도 대상 투수가 나온 경기를 먼저 고정한 뒤 모든 투구의 순서를 만든다.
  단일 사전 비교에서 6.74초에서 0.43초로 줄었으며 응답 전체의 canonical hash가 동일했다.
  투구를 먼저 걸러 자동 판정·선수 교체 경계를 건너뛰는 방식은 사용하지 않는다.

수정 전후 RE24·카운트 RE·승리확률·구장 효과·구종 기대 효과의 **5개 모델 파일 hash가 모두
동일**했다. 성능 변경이 표본·계수·검증 결과를 바꾸지 않았음을 실제 자료에서도 확인했다.

## 실제 수집 자료의 조회

최종 코드로 30회 측정했다. 선수 조회는 2025년 실제 투구가 가장 많은 투수의 3,037구,
집계는 2025 시즌, 경기 가치는 해당 시즌 정규시즌 한 경기다. 고정 모델 조회는 현재 원천
manifest 검증과 worker 적용을 포함한다. DB/OS cache를 비우지 않았으며 HTTP·렌더링은 제외한다.

| ------------------------------ | -----: | ----------: | --------: | -------------: |
| 타격 집계                      |  136.4 |       145.9 |     134.7 |           10.5 |
| 투구 집계                      |   74.1 |        72.1 |      63.9 |            8.0 |
| 구종 모형 입력                 |  265.5 |       267.1 |     187.3 |           86.9 |
| 구장 환경 원 집계              |  550.0 |       611.9 |     606.3 |            9.9 |
| 연속 투구                      |  368.9 |       425.1 |     343.9 |           99.4 |
| 구종 기대 효과·모델 적용       | 1799.1 |      1149.6 |     786.5 |          365.5 |

최대 관측 RSS는 약 745MiB, 구종 기대 효과의 최종 요약은 13.5KiB다. 입력 조회와 연속 투구의
직렬화 크기는 내부 repository 결과로 브라우저 최종 응답 크기와 다르다. 각 부분의 p95는
합산하지 않는다. 15종 SQL 실행계획과 원 측정은 검증 실행의 `benchmark.json`에 기록했다.

구장 효과의 조회 p95는 0.65초까지 줄었다. 구종 기대 효과는 1.15초로 초기 선수 조회 목표
1초를 아직 넘는다. HTTP·브라우저·동시 요청까지 포함한 목표 달성 여부는 별도 검증이 필요하다.
전체 학습의 약 5GiB 메모리 사용량도 남아 있는 개선 대상이며, 화면 요청 중 재학습하지 않는다.

2026-09-20 운영 배포 후 HTTP·브라우저 점검 결과는 [운영 배포 기록](production-deployment.md)에
별도로 기록했다. 구장·구종 기대 효과의 HTTP 재조회 5회 범위는 각각 577–649ms·1,071–1,178ms다.
매치업·투수 변화·데이터 품질은 추가 재조회에서도 각각 8.41초·9.35초·14.70초가 걸려 병목이
남아 있다. 이 소수 표본과 동시 요청 2건의 성공으로 p95 또는 부하 상한을 판단하지 않는다.

후속 수정에서 매치업의 넓은 view·투구별 반복 join, 투수 변화의 불필요한 시즌 전체 읽기,
품질 캐시 확인 이전의 집계를 줄였다. 동일 사본에서 매치업 약 1초, 저장 기준을 재사용한 투수
변화 첫 조회 156ms, 품질 재조회 139–148ms를 관측했다. 표본·초기 계산 비용·해시 동등성은
[후속 개선 기록](2026-09-20-improvements.md)에 구분했다.

후속 운영 배포의 HTTP 첫 조회 / 다음 4회는 매치업 1,279ms / 1,011–1,090ms,
투수 변화 699ms / 18–22ms, 데이터 품질 4,070ms / 132–137ms였다. 보정·기준 파일을
준비한 상태이며 시즌 전체 최초 계산 비용과 동시 요청 부하는 이 범위에 포함하지 않는다.
2025 승리확률도 새 모델로 준비 상태이며 실제 7경기의 HTTP 응답은 279–417ms였다.

최종 `pnpm performance` 회귀 검증에서 컴파일 평균 5.361ms / p95 7.785ms,
재생 구성 평균 1.138ms / p95 1.744ms로 기존 기준을 유지했다.

## 구질 매치업과 원천 진입각 추가

후속 매치업 모델 학습은 실제 1,318,591구에서 96.09초, 100ms 간격 최대 관측 RSS 3.47GiB였다.
조회부터 학습까지 한 worker가 입력을 소유하도록 바꿔 원시 투구 복제를 제거했다. 첫 구현의
4.71GiB보다 약 26% 적으며 같은 모델 hash를 얻었다. 화면 요청에서는 학습하지 않는다.

2025년 3,037구 투수와 2,450구 타자를 대상으로, 무거운 다른 검증이 끝난 뒤 30회 순차 측정했다.
DB/OS cache는 비우지 않았고 모델 파일의 strict 검증·현재 manifest 비교·DB 읽기·worker 적용을
포함하며 HTTP·렌더링은 제외한다.

| 새 조회                    | 첫 ms | 이후 29회 p95 ms | 입력 읽기 p95 ms | worker p95 ms |
| -------------------------- | ----: | ---------------: | ---------------: | ------------: |
| 구질 매치업·타자 기대 반응 | 2,284 |            1,412 |            1,382 |            59 |
| 원천 VAA/HAA               |   181 |              171 |              150 |            22 |

각 부분의 p95는 합산하지 않는다. 매치업은 여전히 초기 선수 조회 목표 1초를 넘으며 학습 원천의
선수 키 manifest 조회/해시 계산이 주된 비용이다. 고정 스키마의 검증기를 재사용하지만 원천 검증을
생략하거나 TTL 캐시로 대체하지 않는다. 이전 측정은 DB 통합 테스트와 동시에 실행했으므로 그
2.26초와 이번 1.41초의 차이 전체를 코드 개선 효과라고 판단하지 않는다. 두 응답 hash는 동일하다.

원 측정과 실제 평가 결과는 [구현·검증 기록](2026-09-20-matchup-angles.md)에 연결했다.

운영 배포 후 HTTP 첫 조회 / 이후 4회는 매치업 1,924ms / 1,292–1,609ms,
진입각 184ms / 177–218ms였다. 실제 모델과 원천 검증을 포함하지만 5회 표본의 범위이며
p95나 부하 상한은 아니다. 기존 매치업·변화·구종 기대 효과·11회 승리확률도 정상 응답했다.

## 모델 운영 후속 최적화

전체 시즌 운용과 HTTP의 반복·동시·취소 검증 명령은 `analysis:audit`다. 2026-09-21의 실제
1,729개 선수·시즌 응답 불변성, 관측 시간·RSS와 최초 보정 계산의 남은 비용은
[전체 시즌 검증](2026-09-21-full-audit.md)에 구분했다. 첫 조회와 warm p95를 혼합하지 않는다.

같은 snapshot의 원천 지문으로 유효 신장 manifest hash를 재사용한다. 운영 매치업 HTTP 첫 조회는
1,762ms, 예열 후 30회 순차 측정의 첫 값은 768ms, 다음 29회의 p95는 712ms였다. 응답 hash는
이전과 같고 동시 부하 상한을 뜻하지 않는다. 구질 새 갱신 worker의 최대 관측 RSS는 3.74GiB로,
이전 CLI의 5,142MiB보다 약 25% 줄었다. 기존 구질·매치업 모델 hash를 정확히 재현했다.
측정 조건과 검증 결과는 [모델 운영 기록](2026-09-20-model-operations.md)을 따른다.
