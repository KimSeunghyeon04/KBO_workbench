# 모델 운영과 조회 검증

2020–2025 적용 시즌을 선택해 여섯 모델의 상태·기간·갱신 작업을 확인한다. 실제 학습 가능 범위는
일반 모델 2023–2025, 승리확률 2025다. 날짜상 학습 가능과 실제 데이터의 검증 통과는 별개다.

## 시즌별 기간 정책

| 적용 시즌 | 최종 학습                     | 후보 비교용 검증 시즌 | 적용 시즌 평가  | 승리확률                              |
| --------- | ----------------------------- | --------------------- | --------------- | ------------------------------------- |
| 2020–2022 | 선행 자료 또는 검증 이력 부족 | 두 시즌 미확보        | 모델 제공 안 함 | 2020/2021 규정 미지원, 2022 이력 부족 |
| 2023      | 2020–2022                     | 2021, 2022            | 2023            | 검증 이력 부족                        |
| 2024      | 2020–2023                     | 2022, 2023            | 2024            | 검증 이력 부족                        |
| 2025      | 2020–2024                     | 2023, 2024            | 2025            | 2022–2024 학습, 2023/2024 검증        |

검증 시즌마다 그 이전 자료로 전처리·기준 궤적·보정·계수를 다시 적합한다. 마지막 두 선행 시즌의
기존 채택 기준을 통과한 후보를 고정한 뒤 전체 과거 자료로 적합하고 적용 시즌을 평가한다.
적용 시즌 이후 행은 읽지 않는다. 적용 시즌의 결과는 선택·전처리·계수에 사용하지 않는다.
RE24/카운트의 단순 기준표와 각 모델의 기존 표본·수렴·하위집단 gate는 유지한다.
두 검증 연도의 결과가 필요한 복잡한 후보는 한 연도만으로 채택하지 않는다.
현재 지원하는 승리확률 학습 규정은 2022년부터여서 2023/2024용 검증 이력이 부족하다.
2025의 11회 종료 재구성은 그대로 사용하며 과거 원장과 봉인 fact는 변경하지 않는다.

순수 `model-training-period` 모듈은 기간과 지원 여부만 계산한다. 지표별 적합과 채택은 각 모듈에
남긴다. 파일 읽기·저장에서도 검증 시즌/최종 평가 시즌과 기간 지원 여부를 확인한다. 따라서 이전에
고정된 2023/2024 검증 연도를 잘못 사용한 과거 시즌 파일은 재사용하지 않는다.

## 책임

- contracts: 모델 상태, 갱신 요청, 작업 단계와 자동 갱신 설정의 strict DTO.
- persistence: 기존 모델별 manifest/검증/파일 공개를 유지한다. 원천 확인 repository와 writer lock을 따르는 작업 저장소만 추가한다.
- server: 정해진 여섯 모델을 순서대로 조립한다. 범용 모델 등록기나 플러그인 계층은 만들지 않는다.
- training worker: 자체 읽기 전용 DB snapshot에서 자료를 읽고 같은 heap에서 기존 순수 학습 함수를 호출한다. 원시 투구를 API heap으로 복제하지 않는다.
- web: 상태와 검증 채택 수, 작업 진행·취소·실패를 표시한다. 계산이나 모델 채택을 결정하지 않는다.

## 갱신

전체 시즌에서 한 번에 한 작업만 허용한다. 한 작업은 하나의 적용 시즌에 묶이며,
RE24 → 카운트 → 승리확률 → 구장 → 구질 → 매치업 순서다. 이력 부족 모델은 강제 학습에서도 제외한다.
현재 원천과 같은 모델은 건너뛴다. 모델별 검증이 허용한 추정만 기존 소비 경로에서 사용한다.
학습 뒤 원천 hash와 매치업의 기반 모델 hash를 다시 확인하고 기존 workspace 저장기로 공개한다.
공개 직후 원천이 바뀌는 경우에도 조회 경로가 다시 검증하므로 오래된 모델을 적용하지 않는다.
각 모델의 공개는 원자적이며 여섯 모델 전체를 하나의 트랜잭션으로 취급하지 않는다.

요청 UUID가 작업 identity이자 멱등성 키다. 같은 UUID의 시즌·강제 학습·trigger가 다르면 409다.
실행 요청·단계는 공개 응답 전에 atomic 파일로 저장한다.
재시작 시 미완료 작업을 중단 실패로 표시하고 자동 재개하지 않는다. 완료 모델은 유지한다.
취소는 현재 worker를 종료하며 이미 공개한 모델은 되돌리지 않는다. 작업 오류는 화면에 남긴다.
자동 갱신은 시즌별로 켜는 영속 설정이며 기본은 모두 꺼짐이다. 켜면 즉시 확인하고 이후 6시간마다
활성 시즌을 순서대로 점검한다. 이전 시즌 작업을 마친 뒤 다음 시즌을 실행해 worker·메모리 사용을
겹치지 않는다. 실패 재시도도 다음 점검까지 기다린다. 화면의 시즌 선택만으로 설정이 바뀌지 않는다.

## 작업 메타데이터 계약 결정

시즌을 작업 identity에 추가하기 위해 작업·자동 갱신 파일을 **version 2**로 명시적으로 확장했다.
모델 자체의 version/hash 형식과 `through-<연도>.json` 포인터는 유지한다. DB migration은 없다.
이전 작업/설정은 별도 strict legacy schema로만 읽고, 당시 유일한 적용 시즌인 2025로 해석한다.
조회는 파일을 다시 쓰지 않는다. 이후 해당 작업 상태나 설정을 저장할 때 v2로 기록한다.
버전이 없는데 시즌 필드가 있거나 알 수 없는 필드가 섞인 파일은 legacy로 통과시키지 않는다.

GET `/api/v2/analysis/models?season=2023`은 선택 시즌 상태와 전체 최근 작업을 반환한다.
POST `model-jobs`는 `requestId`, `force`, `applicationSeason`을 요구한다.
PUT `model-policy`는 `enabled`, `applicationSeason`으로 해당 시즌만 변경한다.
2020–2022 수동 갱신은 409, 자동 갱신 설정은 400으로 거부하며 화면에서도 비활성화한다.

## 조회 비용

유효 신장 hash만 pool별 최대 다섯 학습 기간에 재사용한다. 매 요청의 동일 repeatable-read snapshot에서
현재 revision/document/source bundle, sealed 신장 dataset, 선수별 고정 신장 선택의 SHA-256 지문을 읽는다.
게임 facts·봉인 dataset·신장 선택의 불변성과 이 지문을 함께 이용한다. 경기 분류와 분류 dataset hash는
기존 manifest 경로에서 매번 확인한다. TTL만으로 최신성을 판단하지 않으며 원천·모델·응답 hash 계약은 그대로다.
각 모델은 필요한 기간만 읽는다. 카운트 모델의 같은 학습 기간에 대한 RE24 사전표는 후보 사이에서
재사용하며 한 학습 호출 안에서 최대 세 개의 24상태 표만 보관한다. 후보 검증 자료가 없어도 날짜만
옮겨 기존 계수를 복사하지 않는다. 다른 시즌 파일 공개는 기존 2025 포인터를 변경하지 않는다.

## 검증

작업의 중복 요청, 순서·건너뛰기, 취소, 실패, 재시작, 원천 변경과 기반 모델 변경을 회귀 검증한다.
DB에서 신장 보충·revision·분류 변경 시 캐시 무효화를 확인한다. 실제 자료의 응답 hash를 비교하고
같은 요청의 cold/warm 시간을 기록한다. 계약·서버·화면 테스트와 격리 DB/E2E 및 기본 품질 게이트를 실행한다.
