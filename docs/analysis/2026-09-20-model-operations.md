# 모델 운영·원천 검증 최적화 결과

2026-09-20. 2025 시즌용 여섯 모델의 상태·갱신·취소·자동 점검을 구현하고 운영에 반영했다.
설계와 책임 경계는 [모델 운영 설계](model-management.md)를 따른다.

## 구현과 운영 상태

- `/analysis/models`에서 학습 종료 시즌, 적용 시즌, 최신 여부, 검증 채택 수와 최근 작업을 확인한다.
- 필요한 모델만 갱신하거나 전체 재학습할 수 있다. 구질 이후 매치업 순서로 하나씩 실행한다.
- 작업은 요청 UUID로 중복 실행을 막고 진행 상태를 저장한다. 중단·재시작 시 이미 공개한 모델을 유지한다.
- 학습 중 원천 또는 기반 모델이 바뀌면 새 포인터를 공개하지 않는다. 조회 때도 현재 원천을 검증한다.
- 자동 갱신은 영속 설정으로 선택할 수 있고 6시간마다 원천을 확인한다. 운영 기본값은 꺼짐이다.
- 현재 운영 모델 여섯 개는 모두 최신이다. 운영 갱신 요청에서 여섯 모델 모두 재학습을 건너뛰었고,
  같은 요청 ID를 다시 전송했을 때 같은 작업·sequence를 반환했다.

## 실제 자료 학습 재현

운영 DB와 같은 소유권 확인된 읽기 전용 사본, 새 격리 workspace에서 구질·매치업을 순서대로
실행했다. 새 worker가 원시 입력과 학습을 같은 heap에서 처리하며 부모는 모델만 받아 검증·공개한다.
1,318,591개 입력 투구와 기존 학습/검증 기준을 유지했다. 측정 중 일부 품질/E2E 검증이 병행되었으므로
시간은 이 실행의 관측값이며 처리량 보장이 아니다. RSS는 100ms 간격의 전체 프로세스 관측 최대치다.

| 모델           | 자료 읽기 초 | 학습 초 | 재확인·저장 초 | 전체 초 | 최대 RSS GiB |
| -------------- | -----------: | ------: | -------------: | ------: | -----------: |
| 구질 기대 효과 |        40.05 |  189.01 |           2.13 |  231.19 |         3.74 |
| 투타 매치업    |        37.76 |   52.14 |           0.69 |   90.59 |         3.62 |

구질의 이전 CLI 관측 최대 RSS 5,142MiB에 비해 이번 경로는 약 3,833MiB로 약 25% 감소했다.
두 모델은 모두 기존 운영 모델과 hash가 정확히 같았다.

- 구질: `b336cc982fd639030ed9aabcf3bb2fbcaabd0864060b99d192597995992c415a`
- 매치업: `33befef06d21c99fe4280216eb2592b2d904f66d1edf6c2735b9401dbe0dffb4`

## 조회 성능과 결과 보존

매 요청에서 같은 snapshot의 current revision·봉인 신장 dataset·고정 신장 선택 지문을 읽는다.
지문이 같으면 신장 manifest hash를 재사용한다. 경기 분류·분류 dataset은 기존 경로에서 매번
검증한다. TTL에 의존하지 않고 기존 source/model/response hash 정의를 보존했다.

운영 HTTP의 첫 매치업 조회는 1,762ms였다. 이후 상태/회귀 점검으로 예열한 같은 요청을 30회
순차 실행했으며, 첫 측정 768ms, 다음 29회의 p95는 **712ms**였다. 실제 모델 읽기·원천 검증·
두 선수 자료 읽기·worker 계산·HTTP를 포함한다. DB/OS cache를 비우지 않았으며 동시 부하 상한을
뜻하지 않는다. 초기 조회에는 여전히 별도 비용이 있다.

기존 21개 HTTP 점검도 모두 통과했다. 구질 기대 효과는 488ms, 11회 승리확률은 382ms였으며
매치업·각도·기존 매치업·투수 변화의 비교 응답은 기존과 같았다. 별도 DB 통합 검증과 동시에
실행했던 초기 repository 측정(p95 1,126ms)은 운영 HTTP 최종 결과와 섞어 비교하지 않는다.

## 검증·데이터 보호

- unit/API/UI 849개(architecture 17개 포함), 격리 PostgreSQL 71개 통과.
- lint, format, typecheck, schema, build 통과. 마지막 버튼 스타일 수정 뒤 UI 테스트·웹 빌드와
  운영 브라우저의 데스크톱/390px 화면을 다시 확인했다. 가로 넘침과 콘솔 오류는 없었다.
- 격리 Compose E2E에서 여섯 worker의 학습·공개, 중복 요청, 재시작 뒤 파일/작업 유지와 기존
  import/replay/교정/기록정정/backup/restore 흐름을 검증했다.
- 취소 중 진행 파일 쓰기가 끝나기 전에 종료 상태를 기록하지 않도록 순서를 고정하고,
  worker의 결과 전송 직후 종료되는 경우도 회귀 테스트로 고정했다.
- 신장 dataset·고정 선택·revision·경기 분류 변경 뒤 캐시가 원천과 일치하는지 확인했다.
- compiler 평균 4.723ms/p95 6.231ms, replay 평균 0.979ms/p95 1.415ms로 기준을 유지했다.
- 운영 4,693개 sealed revision의 document/projection 목록 hash는
  `a5513d414d218d2635ebbe7504c8c193a7b9c0d844036e33090e832ffa351246`로 동일하다.
  current/active 파일 11개도 동일하고 여섯 운영 모델 hash와 자동 갱신 설정을 보존했다.
  새 DB migration은 없으며 기존 head `0012_competition_game_links`를 유지했다.
- 배포 이후 수집한 API 로그에서 warning/error와 5xx는 0건이었다.

실행 결과는 로컬 `analysis/deployment/20260920-model-ops/`의 `training.json`,
`http-management.json`, `http.json`, `integrity.json`, `e2e-final.log`, `test-final.log`,
`integration.log`에 보관한다. 과거 시즌별 모델 확장과 추가 투수 운용 모형은 이번 범위에 포함하지 않는다.
