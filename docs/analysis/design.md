# 분석 기능 전체 설계

작성일: 2026-09-20. 상태: 제안. 현재 구현의 계약을 즉시 변경하는 문서가 아니다.

## 1. 목적과 범위

현재 sealed 경기 기록으로 선수 성적, 투구 특성, 타자 반응, 배합, 운용, 득점·승리 기여를 분석한다.
각 숫자에서 계산 정의·분모·제외 사유·경기 또는 투구 근거까지 확인할 수 있어야 한다.
외부 자료는 경기 종류 분류와 선택적인 과거 날씨처럼 입수가 간단한 범위만 사용한다.
실측 회전·정밀 타구·동작 자료를 요구하는 기능은 범위 밖이다.

첫 제품 단위는 A01의 작은 품질 표시와 A03의 투수 프로필이다. 모든 공통 계층을 먼저 완성하는
방식으로 진행하지 않는다. 기능 범위와 제외 목록은 [자료 문서](data-sources.md)를 따른다.

## 2. 현재 구조와 확장 위치

```text
원본 증거 → collection → 교정 가능한 원장 → game-core compile → sealed PostgreSQL
                                                              ↓
                                               current typed facts + 확정 보조자료
                                                              ↓
                                       persistence: 기능별 표본 조회·검증·snapshot
                                                              ↓
                                  server: 요청 조립·제한된 계산·캐시·응답 검증
                                      ↙                       ↘
                         game-core: 순수 계산             web: 표·지도·비교·근거
```

| 소유 위치              | 새 기능에서 맡을 책임                                            | 맡지 않을 책임                             |
| ---------------------- | ---------------------------------------------------------------- | ------------------------------------------ |
| `packages/contracts`   | 기능별 strict TypeBox query/response, 단위·상태·분모 계약        | SQL, 학습 실행, 화면 설정                  |
| `packages/game-core`   | 이미 계산된 fact를 입력으로 받는 순수 통계·기하·모형 평가 함수   | 원문 파싱, DB 조회, 경기 규칙 재실행       |
| `packages/collection`  | 외부 일정·날씨 응답의 취득·정규화·근거 보존용 adapter            | 보조자료의 DB 저장, 분석 상태 추정         |
| `packages/persistence` | 기능별 SQL, strict hydration, 일관된 입력 snapshot, 파일/DB 보존 | 웹 지표 정의, 원본 또는 sealed fact 교정   |
| `apps/server`          | 서비스·route·worker 조립, 취소·동시 실행 상한, 모델 준비 명령    | 범용 쿼리 언어, 새로운 야구 상태 계산기    |
| `apps/web`             | 기능별 page/controller/panel, URL 조건, 서버 결과 표시           | 지표 재계산, 자동 데이터 보완, 의학적 해석 |

새 workspace package는 만들지 않는다. 순수 분석 함수가 늘면 기존 패키지 안에 의미별 파일을 둔다.
패키지 간 접근은 명시적인 `src/index.ts` named export만 사용한다.

기존 진입점은 `PitchAnalysisRepository`, `PitchAnalysisService`, `BatterDisciplineRepository`,
`BatterDisciplineService`와 해당 routes다. 이들을 상속하는 `BaseAnalysisService`는 만들지 않는다.
현재 repository에 계산 조립이 일부 섞여 있다는 이유만으로 전 기능을 먼저 재작성하지 않는다.
새 기능이 순수 계산을 두 번째로 요구할 때 그 계산만 game-core로 옮기고 기존 호출 결과를 고정한다.

## 3. 추상화 기준

| 대상                   | 이번 설계의 결정                                         | 공유 또는 분리를 판단할 증거                                   |
| ---------------------- | -------------------------------------------------------- | -------------------------------------------------------------- |
| 기능 서비스·repository | 구체적인 클래스/함수와 명시적 SQL을 유지                 | 필터, grain, 기준 집단이 기능마다 다름                         |
| 비율·표본 표시         | 작은 비율 결과 계약과 표시 컴포넌트만 공유 가능          | 같은 분자/분모/null/단위 의미의 실제 소비자 2개 이상           |
| 실제 코스 분류         | A04/A07에서 같은 좌표·키 정책을 사용할 때 순수 함수 공유 | 기존 경계 테스트의 결과가 양쪽에서 일치                        |
| 구질·선구안 좌표       | 서로 다른 타입과 함수로 유지                             | 같은 시각 정렬 위치와 각자 도착 위치는 정의가 다름             |
| 경기 scope와 snapshot  | A01/A03에서 필요한 필드부터 도입                         | 필터와 기준 집단의 차이가 계약에 명시되어야 함                 |
| 계산 worker·캐시       | 기존 bounded 실행과 cache 도구를 조합                    | 새 기능마다 무제한 worker/pool을 추가하지 않음                 |
| 지표 목록              | 코드·문서에 명시적 필드로 작성                           | `metricId → 수식 문자열` 또는 임의 실행 registry를 만들지 않음 |
| 화면                   | 표본 배지·빈 상태 등 표현만 공유                         | 서로 다른 화면을 JSON 설정으로 생성하지 않음                   |
| 외부 보완              | 일정·날씨 각각 구체적인 adapter와 저장소                 | `ExternalDataProvider<T>` 같은 선행 추상화 불필요              |

공통화 PR에는 실제 소비자 두 곳, 같은 불변식, 각 소비자의 회귀 테스트를 제시한다. 그 근거가
없으면 기능 파일에 남긴다. 반대로 분모나 코스 경계처럼 동일한 도메인 규칙을 복사하지도 않는다.

## 4. 분석 모집단과 identity

### 4.1 경기 범위

- 기본 신규 분석은 확인된 정규시즌의 선택 연도·날짜 범위다. 시범·포스트시즌은 명시적으로 선택한다.
- 경기 종류 미상은 정규시즌에 편입하지 않는다. 품질 화면에 미분류 수를 표시하고 탐색용 포함은 별도 선택이다.
- 기존 두 화면은 현재의 전체 수집 경기 범위를 먼저 명시한다. 경기 종류 필터를 추가하는 배포에서
  기본 범위 변경과 기준값 재계산을 함께 적용하고 URL·응답·캐시 키에 범위를 포함한다.
- 현재 sealed revision만 사용한다. 원장·quarantine·관찰 상태로 결과를 보충하지 않는다.
- 2020–2025 자료가 있다는 것과 각 시즌의 공식 모든 경기가 있다는 것은 다르다. 일정 대조 전에는
  ‘리그 전체’ 대신 ‘수집 경기 기준’으로 표시한다.

최초 query는 단일 season, 같은 시즌 안의 dateFrom/dateTo, competition, 대상 선수와 그 기능에
필요한 필터만 허용한다. 시즌 간 화면 비교는 각 시즌 결과를 나란히 조회한다. 임의 다차원 검색과
전 기간 원시 투구 다운로드는 첫 구현에 넣지 않는다.

### 4.2 표본 단위와 연결

| 단위      | identity와 연결 기준                                              | 금지되는 연결                                       |
| --------- | ----------------------------------------------------------------- | --------------------------------------------------- |
| 투구      | `game_id + revision + pitch_id`                                   | non-unique `source_pitch_id`로 합치기               |
| 타석      | `game_id + revision + start_event_id`                             | 한 타석 결과를 그 타석의 모든 공에 복제해 타율 계산 |
| 플레이    | `game_id + revision + play_id` 또는 해당 play_sequence            | atomic play를 이동 행마다 나눠 가치 중복 부여       |
| 주자 이동 | 같은 revision의 play + movement identity                          | 문자열 이름만으로 주자·책임 투수 합치기             |
| 선수      | 기존 player identity/canonical 매핑; 미해결은 제공자 ID 범위 유지 | 이름 일치만으로 시즌·선수 병합                      |

타석의 기록 귀속은 compiler fact의 타자·투수 및 공식 집계를 따른다. 실제 투구를 던진 선수와
볼넷·삼진 기록 책임 선수가 다를 수 있으므로, 구질 분석의 투수와 공식 성적의 투수를 혼용하지 않는다.
이닝·주자·득점 상태는 typed before/after fact를 읽으며 분석 코드에서 야구 규칙을 다시 계산하지 않는다.

### 4.3 지표별 표본

1. 실제 투구 여부는 `actual` fact를 따른다. 자동 볼/스트라이크·no_pitch는 실제 투구 분모에서 제외한다.
2. 성적 집계는 공식 PA/AB/BF 플래그를 따른다. partial PA의 실제 투구는 유지하지만 공식 타석에 넣지 않는다.
3. 구속·구종 존재, 유효 궤적, 코스·존 판정 가능, 보정 가능 표본을 각각 센다. 전체에 가장 강한 필터를
   일괄 적용하지 않는다. 예를 들어 트래킹이 없어도 타율 집계에는 포함한다.
4. 상호 배타적인 첫 제외 사유를 집계해 `전체 = 사용 + 제외`를 검증한다. 여러 품질 문제의 진단 수는
   별도 표로 표시하며 합산 가능한 제외 수처럼 사용하지 않는다.
5. 소표본 결과는 탐색 표에 분자·분모와 함께 남긴다. 순위 진입 기준은 기능별 명시적 정책으로 분리한다.

## 5. 좌표·보정·기준 집단

### 5.1 두 좌표의 계약 보존

- **구질 비교:** 기존 중간면 17/24ft, 같은 시각 정렬 모델과 구장 편향 정책을 사용한다.
  경기일 이전 84일·반감기 7일 등 이미 검증한 보정 설정을 이 작업에서 다시 탐색하지 않는다.
- **실제 코스/선구안:** 원천 cross_plate_x와 원천 cross_plate_y에서의 궤적 높이, 확정된 신장과
  기존 존 정책을 사용한다. 구질 보정치를 스트라이크존이나 실제 코스에서 차감하지 않는다.
- **실제 궤적 조합:** 공통 거리면에서 원천 궤적을 평가한다. 끝점의 구장 보정만으로 비행 전 구간이
  교정되었다고 간주하지 않는다. 구장·시즌별 비교와 제한을 함께 표시한다.
- 50ft의 초기 위치는 실제 릴리스 위치가 아니다. VAA/HAA를 추가하면 원천 궤적에서 유도한 각도라는
  별도 정의·단위·면·유효성 검증이 필요하며 기존 보정의 정확성을 자동 승계하지 않는다.

미보정 유효 투구는 현재 정책대로 탐색할 수 있지만, 원인과 수를 표시한다. 보정 완료 표본끼리의
비교와 미보정 포함 비교를 한 시계열의 같은 선으로 조용히 연결하지 않는다.

### 5.2 기준을 바꾸는 필터와 표시만 바꾸는 필터

각 기능은 `분석 대상`, `기준 집단`, `표시 선택`을 구분한다. A03의 점 숨김·군집 색상은 평균 포심이나
기준 분포를 다시 학습시키지 않는다. A07은 기존 선택 타자 제외·조건 일치·최소 비교 표본을 유지한다.
새 정규시즌 범위는 보정 입력과 평균 기준에도 명시적으로 적용하며 scope를 hash에 포함한다.

기간 비교의 기본 구질 좌표는 해당 시즌의 같은 기준 궤적에 정렬한다. 서로 다른 기준으로 계산한
전월/이번 달 좌표를 차감하지 않는다. 시즌 간 비교는 시즌별 기준 차이를 표시하고 원 구속·공통
기하량을 따로 제공한다. 시즌 상대좌표의 차이를 그대로 절대 구질 변화라고 부르지 않는다.

## 6. API와 화면

기존 `/api/v2/analysis/pitch-shape`와 `/batter-discipline` 경로를 유지한다. 신규 경로는 기능별 계획에
명시한다. 아래 필드는 신규 응답에 필요한 의미이지 모든 기능을 감싸는 제네릭 응답 타입 제안이 아니다.

| 의미      | 계약에 포함할 내용                                                           |
| --------- | ---------------------------------------------------------------------------- |
| 입력 식별 | 적용 query, 경기 범위, sourceHash, 계산 정의 버전                            |
| 보완 자료 | 실제 사용하는 경기 분류·키·날씨 dataset hash; 사용하지 않으면 의존하지 않음  |
| 표본      | 전체·사용·제외, 지표별 분자·분모, 비교 가능한 표본                           |
| 결과 상태 | ready / empty / insufficient_data / unsupported 등 기능에 필요한 명시적 상태 |
| 모델 결과 | 학습 종료일, 모델 hash, 검증 상태, 적용 가능한 범위                          |
| 근거      | 제한된 표본 목록의 game/revision/pitch 또는 play identity                    |

비율은 0–1로 전달하고 화면에서 %로 표시한다. 차이는 %p와 원 단위를 구분한다. 분모 0은 null,
분모가 양수이고 분자가 0인 경우는 0이다. 선택하지 않은 필터와 ‘미상’ 선택도 구분한다.
strict schema, 최대 조회 범위, 정렬 허용값과 페이지 크기를 route에서 검증한다.

화면은 조건 → 지표·표본 → 분포/추이 → 선택 근거 순서로 구성한다. URL을 조건의 정본으로 유지하고
늦게 도착한 이전 응답이 새 선택의 결과를 덮지 않게 한다. 개별 투구/플레이는 기존 재생의 정확한
revision과 연결한다. 기본 목록은 100행, 상한 1,000행으로 제한하는 것을 최초 목표로 한다.
지표 이름으로 임의 SQL sort를 조립하지 않고 허용된 명시적 매핑을 사용한다.

기능별 구현 파일 수와 메뉴 수를 같게 만들지 않는다. 탐색은 다음 묶음으로 구성한다.

| 화면 묶음      | 포함 기능               | 탐색 방식                                              |
| -------------- | ----------------------- | ------------------------------------------------------ |
| 선수·팀 성적   | A02                     | 선수 선택에서 투수/타자 상세로 이동                    |
| 투수           | A03/A04/A05/A06/A10/A12 | 기존 투구 움직임을 중심으로 코스·변화·배합·운용을 연결 |
| 타자·상대 비교 | A07/A08/A09             | 기존 선구안과 약점 지도, 상대 선택을 연결              |
| 경기·주루      | A11/A13                 | 기존 재생에서 플레이 가치 확인, 선수 주루 표로 이동    |
| 환경·자료      | A01/A14                 | 품질과 구장·날씨를 별도 화면으로 제공                  |

하위 화면 사이에는 시즌·선수·경기 종류·기간 중 의미가 같은 조건만 넘긴다. 타자 ID를 투수 ID로
바꾸거나 표시용 구종 필터를 다른 화면의 기준 집단 필터로 자동 변환하지 않는다.
`app-shell`의 명시적 메뉴와 route를 확장하며 화면 생성용 설정 시스템을 만들지 않는다.

## 7. 조회·저장·계산 비용

### 7.1 snapshot과 cache

- 목록·기준·대상 행은 동일 repeatable-read/read-only transaction에서 읽는다. revision manifest는
  game ID로 명시 정렬하고 보조자료의 적용 선택도 같은 snapshot에서 고정한다.
- 최초 통계 조회는 DB에서 집계한다. 전체 시즌 원시 행을 브라우저로 내려보내지 않는다.
- CPU 계산에 필요한 입력을 확정한 뒤 DB connection을 반환한다. 긴 모델 학습 동안 transaction을 잡지 않는다.
- 새로운 결과 키는 기능·정규화된 조건·관련 sourceHash·정의 버전·실제 사용하는 보정/모델 hash로 만든다.
  기존 캐시의 의미를 바꾸는 범위 변경은 명시적인 키/버전 변경과 회귀 검증을 함께 한다.
- 기존 bounded cache의 용량·실패 제거·동일 진행 요청 공유를 재사용한다. TTL만으로 최신성을 판단하지 않는다.
- 수정된 과거 경기의 revision이나 보완 자료가 바뀌면 영향받는 집계와 학습 결과를 다시 계산한다.
  단순히 오늘 이후 경기만 더하는 증분 처리부터 만들지 않는다.

초기 SQL의 실행 계획과 처리 시간을 측정한 뒤 필요한 인덱스만 추가한다. 인덱스·read view의 추가는
migration으로 관리하되 sealed fact나 projection 계약을 불필요하게 변경하지 않는다.

### 7.2 보조자료와 모델 보존

경기 종류는 source URL/응답 hash/원천 경기 ID/채택 근거를 갖춘 별도 typed reference 테이블에 둔다.
변경 시 새 불변 dataset과 해당 선택을 추가하고 이전 dataset을 덮어쓰지 않는다. 명시적 외래 키와
typed scalar 컬럼을 사용하며 JSONB/ARRAY로 원본 payload를 DB에 넣지 않는다. raw 응답은 별도 파일
증거로 보존한다. seal된 경기 metadata를 수정하거나 game projection의 새 버전을 만들 필요는 없다.

날씨는 A14를 시작할 때만 별도 저장소를 추가한다. 사용하지 않는 자료의 빈 테이블을 먼저 만들지 않는다.
모델은 strict 계약의 계수·학습 입력 manifest·평가 결과를 `.data/analysis/<기능>/...`의 재생성 가능한
파일로 보존할 수 있다. 기존 workspace writer lock, atomic write와 hash 검증을 재사용한다.
경기 DB의 파생 캐시가 사실의 새로운 권위가 되지 않으며 손상 캐시는 삭제/재계산 대상이다.

### 7.3 실행 정책

빠른 SQL 조회와 기존 제한된 구장 보정 갱신은 현행 서비스 흐름을 유지한다. A10/A11/A14의 대량 학습은
명시적 서버 maintenance CLI로 먼저 실행한다. GET 요청에서 여러 모형을 탐색하지 않는다.
준비된 모델이 없으면 기술 통계를 제공하고 모델 미준비 상태를 표시한다.

새 학습은 기본 동시 1개로 제한하고 현재 correction/import worker와 자원을 경쟁시키지 않는 실행
시점을 선택한다. 새 웹 학습 job은 수동 CLI의 소요 시간이 확인된 후 필요할 때만 기존 job 관례로 추가한다.
학습 시간 제한·취소·실패 시 파일 미공개를 검증한다. 임의 함수를 직렬화하는 범용 worker API는 만들지 않는다.

초기 성능 목표는 기존 하드웨어에서 따뜻한 단일 선수 조회 p95 1초, 단일 시즌 집계 p95 2초다.
이는 측정할 목표이며 현재 보장값이 아니다. 첫 30회 반복 측정에서 query/계산/직렬화/RSS를 분리 기록하고,
큰 최초 계산은 준비 상태로 드러낸다. 기존 compiler 평균 10ms/p95 25ms와 기존 화면 응답을 회귀 기준으로 유지한다.

## 8. 모형 검증과 해석

기술 통계와 예측 모형을 UI에서 구분한다. ‘기대 헛스윙’은 관측 자료에서 적합한 조건부 확률이고,
투수의 순수 능력·타자의 실제 인식·최적 전략이나 부상 위험을 뜻하지 않는다.

- 첫 시간 검증은 2020–2022 학습 → 2023 검증, 2020–2023 학습 → 2024 검증으로 한다.
  정의·하이퍼파라미터·채택 규칙을 잠근 뒤 2020–2024 학습 → 2025 평가를 한 번 보고한다.
- 같은 경기의 공은 한 분할에만 속한다. 경기 내 임의 투구 분할을 쓰지 않는다.
- 정규화·구종 기준·평균 포심·소표본 축소·결측 처리·환경 보정 등 학습되는 전처리도 train 범위에서만 적합한다.
  현재 시즌 전체 기준을 이용하는 탐색 화면의 cache를 예측 검증에 재사용하지 않는다.
- 기존 구장 보정 연구에서 2020–2025를 이미 살펴봤으므로 위 평가를 완전히 미접촉한 외부 검증이라고
  부르지 않는다. 새 기간 수집 후 고정된 모형으로 전향 평가하는 것은 별도 단계다.
- current revision으로 다시 구성한 시간 검증은 최신 정정 기록을 이용한 검증이다. 당시 실제로 알려져 있던
  기록만으로 재현한 실시간 성능이라고 주장하지 않는다.
- 분류는 log loss/Brier와 확률 보정, 연속 값은 MAE/RMSE를 함께 기록한다. 시즌·구장·구종·좌우 타석별
  표본과 성능을 분리한다. 신규 투수 제외 검증은 시간 검증과 별도 결과로 제시한다.
- 경기 단위 bootstrap으로 성능 차이의 불확실성을 계산한다. 투구를 모두 독립 표본으로 보지 않는다.
  seed·반복 횟수·입력 정렬을 고정하며 구현 단계에서 결과 재현 오차 기준을 명시한다.
- A10의 최초 채택 기준은 두 검증 연도에서 기준 모형보다 log loss가 낮고, 합산 차이의 95% 구간
  상한이 0 미만이며, 주요 하위 집단에서 큰 악화가 없는 것이다. ‘큰 악화’ 기준은 최종 평가 전에
  상대 log loss 2%와 평가 가능 최소 1,000투구(조건부 모형은 해당 분모)로 고정한다. 기준 미달이면
  단순 모형을 유지한다. 다른 모형의 목표와 기준은 해당 기능 문서에서 별도로 정한다.

첫 화면의 비율은 표본 수와 함께 표시한다. 단순 Wilson 구간을 붙이면 투구 독립 가정의 참고 구간임을
명시하며 선수 차이의 확정 판정에는 쓰지 않는다. 변화·모형 비교의 추론은 경기 단위 재표집을 사용한다.

## 9. 배포와 완료

각 기능은 계약 → 조회/순수 계산 → route/service → 화면 → 근거 이동 → 검증까지 작은 단위로 끝낸다.
새 기능 때문에 기존 투구 움직임·선구안·재생의 정의를 조용히 바꾸지 않는다. migration은 additive하게
적용하고 이전 sealed hash 읽기·검증을 유지한다. 실제 사용자 DB의 교체·재적재는 이 계획에 포함하지 않는다.

기능별 필요한 unit/DB/API/UI 검증과 저장소 품질 게이트는 [구현 계획](implementation-plan.md)을 따른다.
데이터 범위, 분모, 원본 보존, 결정론, 소표본·미지원 상태가 테스트와 문서에 모두 있으면 해당 기능을 완료한다.
