# Critique 기반 프론트 개선 Goal

아래 블록은 PowerShell 스크립트가 아니라 Codex 입력창에 붙여 넣는 `/goal` 프롬프트다.
새 개선 작업을 시작할 때 사용하며, 이미 진행 중인 Goal을 대체하려는 경우에는 먼저 현재
작업의 상태를 확인한다. 목표 점수에 도달할 때까지 무한히 재평가하지 않는다.

Goal의 결과·검증 근거·제약·완료 조건을 함께 정의하는 방식은
[OpenAI의 Goals 안내](https://developers.openai.com/cookbook/examples/codex/using_goals_in_codex)를 따른다.

```text
/goal Impeccable critique를 기준으로 KBO Workbench 프론트의 사용성과 정보 위계를 개선하고,
실제 데스크톱·모바일 브라우저와 회귀 테스트로 효과를 입증하라.

프로젝트: D:/Github/KBO_workbench
대상: apps/web/src 전체. 계획에 그치지 말고 구현·검증·최종 재평가까지 수행한다.
이 작업의 독립 critique 평가자 A/B와 필요한 구현 서브에이전트 사용을 허용한다.

1. 맥락과 기준선
- AGENTS.md, README.md, 구현 명세, PRODUCT.md, DESIGN.md, 관련 docs, 공개 API와
  기존 테스트를 읽는다. kbo-analysis-ui와 docs/analysis/ui-design-workflow.md를 적용한다.
- 코드 경계는 Graft, 필요한 라이브러리 사용법은 Context7으로 확인한다.
- 설치된 Impeccable SKILL.md와 해당 playbook을 따른다. context는 세션당 한 번 실행하며,
  UI 편집 직전에 craft-floor를 읽는다.
- 현재 구현을 독립 critique로 평가하고 Nielsen 10개 항목을 각각 0~4점, 총 40점으로
  기록한다. 기존 보고서는 개선 후보를 찾는 데만 사용하며 현재 문제인지 재확인한다.
- 평가자에게 과거 점수·보고서·목표 점수를 주지 않는다. A는 디자인과 사용 흐름,
  B는 detector와 별도 브라우저 측정을 담당한다. A가 끝나기 전에 detector 결과를
  종합 판단에 넣지 않는다. detector는 평가당 한 번 실행하고 원본을 보관한다.
- 규칙 일치 건수를 사용자 결함 수로 취급하지 않는다. 재현 경로·영향·근거를 붙여
  P0/P1/P2/P3를 구분한다.

2. 개선 범위와 구현
- 재현되는 P0/P1을 우선하고, 핵심 기록·분석 결과의 읽기 순서, 보정 흐름, 상태·오류
  설명, 가독성·키보드·모바일에 영향을 주는 P2를 최대 다섯 문제군으로 정한다.
- 각 문제의 관찰 사실과 완료 기준을 먼저 기록한다. 범위와 우선순위는 이 기준에
  따라 판단하며 반복해서 선호를 묻지 않는다. 새 제품 결정이 필요한 경우만 질문한다.
- 선수와 조회 범위, 분모·표본·미제공 값·근거 연결을 보존한다. 기록과 분석 결과를
  보조 설정보다 먼저 읽게 하고, 진단 코드는 상세에서 확인할 수 있게 한다.
- typeset/adapt/clarify/distill 등 문제에 맞는 명령만 선택한다. 같은 화면을 여러
  디자인 스킬로 중복 재설계하지 않는다. 가장 작은 소유 모듈에 구현한다.
- 흰색·절제된 녹색의 평탄한 기존 시각 방향, API enum, 저장 계약, compiler 권위,
  canonical index와 서버 session 권위를 유지한다. 새 통계나 해석을 지어내지 않는다.
- 사용자 변경을 보존한다. 관련 없는 리팩터링, 커밋·푸시·배포를 수행하지 않는다.
- .env/.data/.backups와 운영 DB를 노출·초기화·덮어쓰기하지 않는다.
  비식별 fixture와 고유 이름의 격리된 임시 자원으로 검증한다.

3. 검증과 반복 한도
- 필요한 회귀 테스트와 pnpm lint, pnpm format:check, pnpm typecheck, pnpm test,
  pnpm schema:game:check, pnpm build를 실행한다.
- 의존성·공개 export 변경은 test:architecture, 서버-웹 흐름은 격리된 test:e2e,
  DB 동작 변경은 test:integration을 추가한다. 기존 실패와 새 회귀를 구분한다.
- 구현 후 데스크톱·모바일을 묶어 한 차례 검토하고 발견된 문제를 한 번에 수정한다.
  마지막 독립 critique를 최종 브라우저 확인으로 사용한다. 구현 후 전체 시각 검토는
  이 두 차례로 제한하며, 통과한 검사나 전체 critique를 이유 없이 반복하지 않는다.
- 최종 A/B는 새로운 독립 평가자로 구성하고 이전 평가 결과를 전달하지 않는다.
  최초와 동일한 대상·척도로 평가한 뒤 결과를 확정하고 점수를 비교한다.
- 실행하지 않은 브라우저·대비 측정·오버레이·테스트를 실행했다고 쓰지 않는다.
  점수 상승이나 임의 목표 점수 자체를 완료 조건으로 삼지 않는다.

4. 완료와 보고
- 선정한 문제의 완료 기준이 실제 브라우저와 필요한 테스트로 입증되고 새 회귀가
  없으며 최종 독립 critique가 끝났을 때 Goal을 완료한다.
- 필수 문제가 남거나 검증이 불가능하면 완료로 표시하지 않는다. 남은 작업,
  확인한 증거와 필요한 조건을 구체적으로 보고하고 Goal 상태 규칙을 따른다.
- 임시 서버·탭·테스트 자원을 정리하고 최종 diff에서 사용자 데이터와 무관한
  파일만 변경되었는지 확인한다.
- 개선별 변경·검증 근거, Nielsen 10개 점수와 총점의 전후 비교, 차이의 이유와 한계,
  남은 P0/P1/P2, 기존 실패·미검증 항목, 변경 파일·보고서·캡처 링크를 보고한다.
```
