# 전체 시즌 운용 비교와 HTTP 조회 검증

2026-09-21. 검증 명령은 `pnpm analysis:audit --run <기존 검증 실행>`이다.
새 실행마다 별도 `audits/<UUID>/`를 만들고, 기존 격리 DB의 소유권과 읽기 전용 연결을 확인한다.
운영 원장·봉인 fact·분류·학습 모델은 수정하지 않는다. 상세 인자는 [검증 절차](real-data-validation.md)를 따른다.

## 검증 범위

2020–2025 수집 자료 중 확인된 정규시즌의 선수·시즌 1,729건, 실제 투구 1,318,591개를 점검했다.
0구 등판도 선수 목록에 포함했다. 비교 입력과 별도로 센 actual pitch 합계, 항목별 제외 합계,
역할 근거, 지표 분모, 평균·확률의 유효 범위, 표본 문턱과 null 정책을 확인했다. 모든 선수를
입력 순서 반전 후 다시 계산했고, 코드 변경 전후 응답 hash를 비교했다.

총 57,057개 지표·집단 비교 중 7,616개(13.3%)를 제공할 수 있었다. 나머지는 공통 표본 부족
48,698개와 재표집 불안정 743개다. 시즌별 제공 비율은 약 12.3–13.7%였다. 선수마다 33개의
고정 비교를 만들므로 특정 휴식·투구량 구간에 관측이 없는 선수도 분모에 포함된다. 이 비율은
오류율이나 선수의 성과 순위가 아니다. 표본 기준을 낮추지 않았으며 개별 결과의 인과성을 주장하지 않는다.

## 계산과 모듈 경계

검증은 `scripts`가 기존 repository·순수 계산·worker·HTTP route를 호출한다. 별도의 production
계산기나 범용 분석 프레임워크를 만들지 않았다. 비교 검사·전체 투수 순회·HTTP 측정의 책임만
분리했다. 운영에서 사용하는 JSON/분모/보정 계약은 변경하지 않았다.

CPU 프로파일에서 canonical key의 반복 NFC 정규화와 일별 보정의 반복 문자열 생성이 관측됐다.
이미 NFC로 정규화한 object key는 다시 정규화하지 않고 같은 비교 연산으로 정렬한다. 보정은
기존 JSON 정렬 키와 투수·구종·월 그룹 키를 셀마다 한 번 만들고, 기준일의 날짜 변환도 재사용한다.
숫자 연산·정렬 결과·보정 계수 정의는 유지한다. 시즌 투구 입력은 같은 strict schema를 미리 컴파일해 검증한다.

## 측정의 한계

HTTP는 localhost 임시 서버에서 실제 route와 worker 1개/대기 16개, DB 최대 4연결로 측정한다.
각 조회의 첫 요청과 이후 30회, 4건씩 10묶음의 동시 요청을 구분한다. 2025 최다 투구 투수를 사용했고
브라우저·운영 프록시는 포함하지 않는다. DB/OS cache는 비우지 않았으며 첫 품질 조회는 별도의 새
보정 캐시 생성 비용을 포함한다. 운용 요청 취소가 worker에 전달되는지와 후속 정상 응답도 확인한다.

원천·모델이 바뀐 실행은 같은 응답의 성능 비교로 취급하지 않는다. 실패·취소한 실행은 기준으로
재사용할 수 없다. 개별 응답과 hash, 실패 행, 시즌 집계, 관측 RSS, HTTP 측정과 실행계획을 파일로
보존하므로 이후 코드·자료 변경에서도 같은 검증을 반복할 수 있다.

## 실제 측정 결과

| 조회           | 첫 요청 ms | 이후 30회 p95 ms | 4건 동시 요청 p95 ms |
| -------------- | ---------: | ---------------: | -------------------: |
| 데이터 품질    |     10,147 |              152 |                  230 |
| 구종 기대 효과 |      1,171 |              450 |                  584 |
| 운용 조건 비교 |        161 |              147 |                  268 |

모든 순차·동시 응답은 같은 조회의 hash와 일치했고, 운용 HTTP 취소 후 worker 복구와 정상 응답을
확인했다. 종료 시 DB 연결은 4개 모두 idle이고 대기 연결은 0이었다. 전체 검증 프로세스의 관측
최대 RSS는 약 1,307MiB였다. 전체 선수 검증·계절 보정·worker 교체가 포함된 값으로 개별 조회의
순수 추가 메모리나 운영 서버의 메모리 상한으로 해석하지 않는다.

변경 전 첫 품질 조회는 9,567ms, 구종 기대 효과의 반복 p95는 448ms였다. 이번 측정에서 전체 HTTP
시간의 유의미한 개선은 확인하지 못했다. 반복 문자열 처리 비용은 제거했지만 시즌 전체를 읽고
일별 보정을 처음 계산하는 비용은 남는다. 첫 요청을 포함해 모든 경로가 1초 미만이라고 주장하지 않는다.

전체 1,729개 운용 응답과 품질·구종·운용 HTTP 응답은 변경 전후 hash가 같았다. 실행 결과는
`analysis/validation/4ab857f2-7a6c-4ffb-b971-80e94924b517/audits/` 아래에 보존했다.

- 기준 실행: `bf1e13bd-1362-4acd-b66f-dbc98924b831`
- 최종 전체 대조: `235b692a-04b6-46e4-b446-51bdf6f5f58d`
- CPU 프로파일: `analysis/deployment/20260921-analysis-audit/`

## 회귀 검사

단위/API/UI 874개(architecture 17개 포함), 격리 PostgreSQL 74개, 검증 도구 7개와
lint·format·typecheck·schema·build가 통과했다. NFC key의 삽입 순서·결합 문자·이스케이프·
정규화 충돌은 property/회귀 검사로 고정했고, actor 입력과 전체 학습 입력의 같은 표본을 대조했다.
격리 Compose E2E는 import·재생·교정·분석 화면·모델 worker·재시작·backup/restore를 통과했고
브라우저 page error는 0이었다. compiler 평균 4.817ms, p95 6.957ms로 기존 10/25ms 기준을 유지했다.

기준 실행의 모드·시즌·원천·완료 상태는 전체 재계산 전에 검사한다. 범위가 다른 실제 기준 실행을
지정했을 때 비정상 종료 코드와 실패 기록을 남기고 선수 순회를 시작하지 않는 것도 확인했다.

## 운영 반영

API·웹 이미지를 교체한 뒤 품질·구종 기대 효과·운용 비교의 운영 응답 3개를 격리 검증 결과와
대조했고 모두 같은 hash였다. 기존 보정 파일을 재사용한 운영의 배포 후 첫 조회는 각각
3,398ms·857ms·162ms였다. 한 번의 관측이므로 성능 향상률이나 p95로 해석하지 않는다.

2023–2025 모델 16개, current/active 파일 11개, sealed revision 4,693개의 document/projection
hash가 배포 전후 같았다. migration head는 `0012_competition_game_links`이고 API·웹·DB는
모두 healthy였다. 자동 모델 갱신의 비활성 상태를 유지했으며 배포 후 API 경고·오류·5xx는 없었다.
이전 이미지는 복귀용 태그로 보존했다. 배포와 무결성 근거는
`analysis/deployment/20260921-analysis-audit/`의 `http-before.json`, `http-after.json`,
`integrity.json`, `deployment.json`, `api.log`에 기록했다.
