# 자동 구장 보정의 계산 비용

2026-09-20, 현재 PC의 Ryzen 5 9600X에서 측정했다. 서비스 구현이나 DB fact는 변경하지 않았다.
선택 모형은 일별 갱신·최근 84일·7일 반감기다.

| 작업 | 측정값 | 범위 |
| --- | ---: | --- |
| 모든 구장 계수 재추정 | 중앙값 32.2ms, p95 47.3ms | 집계된 84일 자료에서 X/Z 동시 추정 |
| 계수와 공분산 재추정 | 중앙값 36.9ms, p95 48.9ms | 투수·경기 2방향 군집 공분산 포함 |
| 평가 대상 과거 596일 프로필 생성 | 22.0초 | 공분산 포함, 순차 처리, 집계 자료 메모리 재사용 |
| 143만 투구 파일 읽기·정리·집계 | 중앙값 3.73초 | 기존 gzip 파일과 경기 manifest 사용, 3회 |
| 82,575개 집계 셀 파일 읽기 | 중앙값 8.6ms | 로컬 pickle 캐시, 5회 |
| 5,000개 표본의 계수 조회·적용 연산 | 중앙값 0.064ms, p95 0.114ms | 메모리 Map 조회와 X/Z 뺄셈만 |
| 1,428,758개 표본의 계수 조회·적용 연산 | 중앙값 12.8ms, p95 14.2ms | 같은 독립 연산 실험 |

회귀 시간은 2025년 5~9월의 15개 기준일에서 각 5회 측정했다. 최근 84일 입력은 3,566~6,009개
투수·경기·구종 셀, 193~326경기다. 고정효과를 그룹 평균 제거로 처리한 후 회귀 행렬의 열은 25~27개였다.
집계 입력 DataFrame 자체의 메모리는 기준일별 약 1.3~2.2MiB, 6시즌 전체는 약 28.5MiB였다.
이 수치는 계산 중 임시 배열과 Python 전체 프로세스의 최대 메모리를 포함하지 않는다.

실행 환경은 Python 3.13.7 / NumPy 2.5.3 / pandas 3.0.6, 적용 연산은 Node 24.19.0이다.
적용 연산 측정은 실제 집계 셀의 게임 키와 평균값을 반복해 지정한 표본 수를 만든 뒤,
미리 준비한 단일 예시 계수표를 적용한 마이크로벤치마크다. 실제 원시 투구 전체를 분석한 시간이 아니다.
DB 조회, 프로필 로딩, 입력 생성, 궤적 계산, 군집화, 응답 직렬화는 포함하지 않는다.
로컬 파일 읽기는 운영체제 파일 캐시의 도움을 받을 수 있으며, PostgreSQL 추출 시간과 프로세스 시작 시간은 제외했다.
과거 596일은 기존 연구의 24개 평가 월에 속한 날짜이며, 6시즌의 모든 날짜를 뜻하지 않는다.

권장 운영 구조는 새 경기나 기록 정정에 맞춰 집계 캐시를 갱신하고, 매일 전체 구장 계수를 한 번 계산해
날짜별 프로필로 보관하는 것이다. 분석 요청에서는 필요한 계수표를 한 번 읽고 경기별로 재사용한다.
각 투구마다 DB에 보정계수를 조회하거나 회귀를 다시 수행할 필요는 없다.
평균 기준·투구 표본·군집 결과에는 보정 프로필의 식별자/해시도 캐시 키에 포함해야 한다.

현재 규모에서 계수 추정과 적용의 추가 산술 비용은 작다. 실제 서비스 지연은 DB 조회·집계·기존 군집화까지
합친 뒤 확인해야 하며, 위 수치를 API 응답 시간 보장으로 해석하지 않는다.
