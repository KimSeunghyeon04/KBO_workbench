# KBO 경기 교정

경기·대상 행이나 공지·반영 범위를 먼저 확정한다. 조사 요청은 근거와 제안까지, 원장 저장 요청은 작업 사본 저장까지, 운영 DB 반영 요청은 새 revision 검증까지 진행한다. 운영 변경은 보정 API 또는 보정 화면과 정상 DB 적재를 사용한다. 원천 번들과 최초 원장은 증거로 보존한다.

## 경기 원장 교정

1. 경기 ID, current sealed revision과 해시, 저장된 작업 사본 유무를 확인한다. 진행 중인 수정이 있으면 그 사본과 revision base를 확인한다. 작업본이 없을 때만 최신 봉인 revision에서 연다. 행 번호는 화면 안내에 쓰고 교정 대상은 이벤트 ID와 endpoint·block·row로 지정한다.
2. 중복 후보는 타석·초말·타자·투수·투구 순번·판정, 앞뒤 행과 관찰 경기 상태를 대조한다. 트래킹의 PTS 순번, 원천 위치와 측정값도 비교한다. 반복 `sourcePitchId`는 검색 단서로 사용한다. 같은 ID를 쓰는 별개의 투구도 있으므로 위치와 투구 문맥을 함께 확인한다. 다른 판정이나 선수·이동 정보를 담은 원천 행은 그 의미를 확인해 보존한다.
3. 같은 공이면 원천 위치와 판정, 메타데이터, 트래킹을 가장 잘 뒷받침하는 행 하나를 실제 투구로 남긴다. 값이 다르면 해당 공과 주변 공의 원본 PTS를 각각 대조하고, 가능한 경우 KBO 중계에서 확인 가능한 항목을 교차 확인한다. 근거가 비슷하거나 후보가 여럿이면 값과 원문 위치를 적어 수동 검토로 남긴다. [중복 투구 교정 사례](references/duplicate-pitches.md)
4. 남기기로 한 행이 `administrative`로 바뀌어 있다면 최초 원장과 원천 증거에서 투구 payload를 확인하고, 해당 행의 identity·원천 위치·관찰값을 유지해 `replace_event`로 복원한다. 확정한 중복 행은 `delete_events`로 삭제한다. 삭제로 기존 tracking link는 제외되고 관측값은 보존된다. 실제 투구와의 대응을 확인한 후보를 `link_tracking_candidate`로 연결한다. 복원·삭제·재연결은 순서대로 하나의 `correction_batch`에 넣는다.
5. 적용 전 preview에서 전후 원장·대상 행·tracking link·차단/경고와 예상한 경기 상태 차이를 확인한다. 투구 메타데이터만 교정하면 점수·실제 투구 수·완료 타석·공식 기록도 대조한다. 같은 session version에서 적용하고 실제 결과를 preview와 비교한다. 차단 0일 때 ready 작업 사본으로 저장한다. `409`나 해시 불일치가 나오면 새 기준과 기존 편집을 다시 읽고 판단한다. [보정 명령과 원천 증거](../../../docs/correction.md)

## KBO 공식 기록 정정

1. `/record-corrections` 검토함에서 공지 원문·정정 전후 값·현재 평가를 읽는다. 경기일, 원정/홈, DH 번호를 current revision에 맞추고, 이닝·초말·타순과 실제 타자·투수를 타석에 대조한다. 미연결 경기는 대상 적재 후 재평가한다. 경기·선수·타석 후보가 모호하거나 공지 전후 값으로 설명되지 않는 충돌은 근거와 함께 수동 검토한다.
2. 공지의 **보정 작업대로 이동**으로 열면 저장된 작업본을 우선 확인한다. 제안에서 판정과 공식 타자·투수 기록 각각의 변경을 읽고, 지원 통계의 정정 후 값과 compiler 계산값을 대조한다. 자책점은 공식값을 확인한다. 생략 필드와 지원 범위는 통계별 계약을 따르고, 확인할 수 없는 타점이나 주자 이동은 원천 증거가 확보될 때까지 판단을 보류한다.
3. 공지 제안 경로에서 미리 본 `proposalHash`와 `expectedSessionVersion`으로 적용한다. 공식값과 계산값이 이미 맞으면 변경 명령 없이 현재 평가를 확인한다. 새 차단 없이 제안이 유효하면 작업 사본을 저장하고, DB 반영이 요청된 경우 아래 적재·검증을 이어간다. [KBO 기록정정 제안](../../../docs/correction.md#kbo-기록정정-제안)

## 운영 반영과 검증

1. 정확한 경기와 저장한 document hash를 지정해 단건 DB 적재를 요청한다. API 사용 시 `expectedDocumentHash`와 해당 적재의 `idempotencyKey`를 보낸다. 중단이나 응답 유실 시 같은 job과 current revision을 먼저 조회한다. 봉인 후 정리만 남았다면 기존 job의 후속 처리 상태를 확인한다.
2. 완료 뒤 새 revision이 current이며 봉인됐는지, document·projection hash가 승인한 결과와 같은지 확인한다. 이전 revision과 해시는 대조해 보존 여부를 확인하고, 적재의 후속 정리가 끝났는지 확인한다.
3. 해당 revision의 replay manifest와 모든 frame page를 읽어 revision·document/frame hash·개수·순서를 확인한다. 대상 이벤트 ID로 유지·삭제와 바뀐 값, 각 투구의 정확한 tracking link를 확인한다. 예상했던 경기 상태와 집계도 대조한다. 공식 기록 정정이면 공지가 **해결됨**으로 재평가되고 승인된 적용 revision과 정정 후 값이 맞는지까지 확인한다.
4. 작업 기록에 기준·적용 revision, 대상 이벤트와 트래킹 ID, 전후 값·집계, 근거·해시와 검증 결과를 남긴다. 검증 불일치가 남으면 그 단계와 관찰값을 기록한다. [PostgreSQL 봉인과 재생](../../../docs/postgresql-persistence.md)
